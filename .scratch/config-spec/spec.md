# 配置规格：把配置镜像收成单一权威

Status: ready-for-agent

来源：架构评审候选 ①（`/improve-codebase-architecture` → `/grilling` → `/domain-modeling`），决策已全部收敛。约束见 ADR 0001 与 ADR 0003。

---

## Problem Statement

同一批配置项在代码里被声明了 5 次，默认值被写了 4 份。

Koishi 管理员看到的症状是：在配置面板里打开一个开关，界面没有变化；或者关掉一个默认开启的开关，它又自己回到开启状态。这类问题没有报错、没有日志，只能靠对着界面反复试。

插件维护者看到的症状是：新增一个配置项要在 6 个地方各写一遍——服务端 Schema 的默认值、下发给控制台的 payload、前端的类型声明、前端的赋值语句、前端 ref 的初始值。漏掉任何一处都不会编译报错，只会静默错。已经积累出的实际不一致有两类：

1. 四个枚举与颜色类配置项在服务端用 `??` 兜底、在前端用 `||` 兜底，空字符串在两侧行为不同。
2. 纯服务端配置项的默认值除了 Schema 还散落在多处 `?? 字面量` 里，其中两个配置项的兜底各写了两遍。

现有测试无法防守这条规则。它们读源码文本、断言「某个文件里必须出现某段字符串」，因此改写法会误报、真改错四端一致性却抓不住。

## Solution

引入**配置规格**：插件全部配置项的唯一权威声明，逐项记录键名、默认值、是否为**镜像配置项**，以及空字符串是否视为未设置。

服务端 Schema 的默认值、服务端代码里的兜底、下发给控制台的 payload、前端**配置镜像**的 ref 初始值与类型，全部从配置规格派生。

对 Koishi 管理员而言，配置面板的分组、字段顺序、控件类型和说明文案完全不变，配置项名称与默认值也不变；变化只是「设置生效」这件事从此可靠。

对插件维护者而言，新增一个配置项从改 6 处变成在配置规格里加一行；漏改会编译报错；「四端必须一致」这条规则由一条守卫测试机器检查。

## User Stories

### Koishi 管理员

1. 作为 Koishi 管理员，我希望在配置面板里改一个观察窗开关后界面立刻按预期变化，这样我不用怀疑是自己看错了还是插件坏了。
2. 作为 Koishi 管理员，我希望关掉一个默认开启的开关后它真的保持关闭，而不是被前端重新兜回默认值。
3. 作为 Koishi 管理员，我希望配置面板的五个分组名称、分组顺序、字段顺序在改造前后完全一致，这样我不需要重新熟悉面板。
4. 作为 Koishi 管理员，我希望单选、颜色、表格这些控件类型和每一条说明文案都保持原样，这样我依赖的操作习惯不被打断。
5. 作为 Koishi 管理员，我希望所有配置项名称保持不变，这样我现有的配置文件升级后继续可用。
6. 作为 Koishi 管理员，我希望强调色留空时界面回落到默认蓝色，而不是渲染成无效颜色。
7. 作为 Koishi 管理员，我希望聊天样式、颜色模式、存储后端留空时都回落到各自默认值，而不是让界面进入未定义状态。
8. 作为 Koishi 管理员，我希望不填好感度 scopeId 时插件按「自动选择」处理，而不是被当成一个空字符串去匹配。
9. 作为 Koishi 管理员，我希望消息缓存条数这类数值配置项填 0 或边界值时行为可预期，而不是被静默替换成默认值。
10. 作为 Koishi 管理员，我希望升级后浏览器里的观察窗不会因为前端产物混入了服务端依赖而变大变慢。
11. 作为 Koishi 管理员，我希望小胶囊的毛玻璃、紧凑阴影、总未读数这几个开关和观察窗的开关行为一致，不因为它们归属不同模块而表现不同。
12. 作为 Koishi 管理员，我希望开发者模拟环境、调试信息这类开发者选项仍然在「开发者选项」分组里，不被这次改造挪位置。

### 插件维护者

13. 作为插件维护者，我希望新增一个配置项只需要在配置规格里加一行。
14. 作为插件维护者，我希望漏掉某一端的声明时编译就报错，而不是等用户反馈才发现。
15. 作为插件维护者，我希望每个配置项的默认值在整个仓库里只写一次。
16. 作为插件维护者，我希望判断某个配置项是不是镜像配置项时只查一个地方。
17. 作为插件维护者，我希望服务端代码里不再出现 `?? 字面量` 这种第二份默认值。
18. 作为插件维护者，我希望同一个配置项的兜底不会在两处各写一遍还写得不一样。
19. 作为插件维护者，我希望「空字符串视为未设置」只在配置规格上声明一次，而不是在每个使用点各写一遍运算符。
20. 作为插件维护者，我希望配置规格能表达「这个配置项没有默认值」，而不是被迫塞一个假默认值。
21. 作为插件维护者，我希望「四端必须一致」这条规则由测试机器检查，而不是靠 review 时人眼比对四个文件。
22. 作为插件维护者，我希望配置相关的测试断言的是运行时行为，而不是源码里出现过哪些字符串，这样重构写法不会误报。
23. 作为插件维护者，我希望删掉那批锁死 Schema 写法的源码断言之后，实际覆盖不下降反而上升。
24. 作为插件维护者，我希望配置面板的分组名和控件类型仍然有断言守着，因为 Schema 形状仍然是手写的。
25. 作为插件维护者，我希望配置规格本身不依赖 koishi，这样前端引用它不会把服务端依赖打进浏览器产物。
26. 作为插件维护者，我希望 `Config` 这个对外导出的类型在使用者的 IDE 里仍然展开成可读的字段列表，而不是一坨展不开的条件类型。
27. 作为插件维护者，我希望现有的 `'../config'` import 路径保持不变，这样这次改造不产生二十多处无关 diff。
28. 作为插件维护者，我希望前端配置镜像仍按领域归属分布，不新建一个被两个前端领域共同依赖的浅 module。
29. 作为插件维护者，我希望观察窗总未读数这类运行时状态不再和配置镜像混在同一个 module 里，这样「四端一致」这条不变量的适用范围是清晰的。
30. 作为插件维护者，我希望这次改造分三批落地，每批之间仓库都处于可发布状态。
31. 作为插件维护者，我希望第一批完全不碰前端，这样出问题时排查范围明确。
32. 作为插件维护者，我希望跨端那一批单独做，便于确认浏览器产物没有混入服务端依赖。
33. 作为插件维护者，我希望这次引入的领域术语在词汇表里有定义，这样后续 issue 和重构建议用词一致。

### 接手实现的 agent

34. 作为接手这个 spec 的 agent，我希望知道每一批的边界和验收方式，这样我不用猜什么时候算完成。
35. 作为接手这个 spec 的 agent，我希望知道哪些现有测试会变红以及各自该怎么处理，这样我不会把守着面板契约的断言一起删掉。
36. 作为接手这个 spec 的 agent，我希望知道测试该打在哪个接缝上，这样我不会为了可测性新增生产导出。
37. 作为接手这个 spec 的 agent，我希望知道哪些约束来自现有 ADR，这样我不会顺手违反已经做过的决策。

## Implementation Decisions

### 配置规格 module

- 覆盖插件全部 31 个配置项，不只是镜像配置项。纯服务端配置项同样在规格里，因为它们的默认值也散落在多处兜底里。
- 每项声明：键名、默认值、是否为镜像配置项、空字符串是否视为未设置。
- 支持「无默认值」形态。好感度 scopeId 是唯一没有默认值的配置项，且不是镜像配置项。
- **不依赖 koishi**。这是硬约束：前端构建的 external 列表不含 koishi，规格一旦引用 koishi 就会被整包打进浏览器产物。
- 需要 `Schema` 的构造代码放在另一个只被服务端引用的 module 里，与规格分文件。

### Schema module

- 形状保持手写：分组划分、分组顺序、字段顺序、单选/颜色/表格控件、数值上下限、全部说明文案都不变。
- 只把默认值改成从配置规格读取。
- 不生成 Schema。生成在框架层面可行，但会丢掉键级字面量类型，且要重写一大块现存断言，收益只是省掉几十行本来很直白的声明。

### 类型

- `Config` 保持手写 interface。它是 npm 包对外导出的类型，派生成映射类型会让使用者的 IDE 提示退化。
- 另加一条**双向键集断言**：配置规格键集与 `Config` 键集必须完全相等，多一个少一个都编译报错。这是「漏改会编译报错」这个收益的实际来源。
- 下发给控制台的 payload 类型与前端配置镜像的 ref 类型**从配置规格派生**，只取镜像配置项。这两个是内部类型，派生没有可读性顾虑。

### 服务端

- 全部 `?? 字面量` 兜底改为读配置规格默认值，包括历史条数、图片缓存三项、运行时 bot 模式、撤回标记、character thinking 显示、模拟环境等纯服务端配置项。
- 下发给控制台的 payload 由配置规格的镜像配置项列表驱动，不再逐项手写。

### 前端

- 配置镜像的 ref 仍由三个领域各自持有（观察窗设置、小胶囊状态、入口状态），不集中。集中会新建一个被两个前端领域共同依赖的浅 module，撞 ADR 0001 的禁止依赖规则。
- 组合根里的赋值改成由配置规格驱动的循环，赋值目标仍是各领域自己的 ref。组合根本来就是允许「创建和传递共享依赖」的位置。
- **观察窗总未读数移出配置镜像所在 module**，进独立的运行时状态 module。它不来自配置、不参与下发，留在配置镜像里会让「四端一致」这条不变量失去明确适用范围。
- 派生的颜色模式留在原处，作为配置镜像的消费者而不是成员。

### 空值语义

- 统一用「仅 undefined/null 才落默认值」。布尔与数值配置项上这是唯一正确选择：用「假值即落默认」会把用户关掉的开关重新打开。
- 四个枚举与颜色配置项（聊天样式、颜色模式、强调色、存储后端）在配置规格上标注「空字符串视为未设置」，由规格的读取函数统一规范化，使用点不再各写运算符。

### 兼容边界（ADR 0001）

- 不改任何配置项名称、默认值、语义。
- 不改 Console 事件名、数据库表名、浏览器本地存储 key。
- 不改 npm 包入口、插件名、构建入口。
- 现有 `'../config'` import 路径保持可用，避免二十多处无关 diff。

### 交付节奏

三批，每批结束仓库都处于可发布状态：

1. **第一批**：建配置规格，Schema 默认值改读规格。只动服务端，前端零改动。
2. **第二批**：服务端全部兜底改读规格。
3. **第三批**：下发 payload 由规格驱动，前端配置镜像的类型与初始值由规格派生，总未读数移出。唯一跨构建根的一步。

## Testing Decisions

### 什么算好测试

只断言外部可观察的行为：配置面板的渲染契约、下发给控制台的 payload、配置镜像的初始值。不断言源码里出现过哪些字符串。

判据：把实现换一种写法而行为不变时，测试必须仍然通过。现存的配置相关断言大多不满足这一条——它们读源文件文本做子串匹配，因此改写法会误报，而真的改坏四端一致性却抓不住。这批断言是这次要替换的对象，不是要保留的资产。

### 接缝

**不新增接缝，不为可测性新增任何生产导出。** 全部断言打在已有的三个读取点上，且优先使用最高的那个。

1. **主接缝（最高）**：插件 `apply` + 内存 Console 替身，取控制台入口回调返回的 payload。这一个接缝就覆盖「Schema → 用户配置 → 下发 payload」整条链，是这次绝大多数断言应该落的地方。
2. **Schema 运行时节点**：从包的公开导出读 Schema 对象本身（默认值、分组列表顺序、控件 role）。这是现有导出面，此前没被用来做行为断言——之前是读源码文本代替。
3. **配置镜像 module 的导出**：直接 import 前端配置镜像 module，读 ref 初始值。

配置规格本身是被服务端和前端共同引用的 module，测试直接 import 它作为被测对象，不算新增接缝。

单一测试文件同时 import 服务端与前端两侧是可行的，仓库里已有先例。

### 新增测试

- **四端一致性守卫测试**：对每个镜像配置项交叉断言「配置规格默认值 = Schema 运行时默认值 = 下发 payload 默认值 = 配置镜像 ref 初始值」四者相等；对每个非镜像配置项断言它不出现在下发 payload 里。这条测试断言的正是配置规格存在的理由。
- **布尔回归测试**：给默认开启的开关传入关闭值，断言下发 payload 仍是关闭。这是防「假值即落默认」回归的关键断言，目前完全没有。
- **空字符串规范化测试**：给四个枚举与颜色配置项传空字符串，断言各自落到默认值。
- **无默认值测试**：断言好感度 scopeId 不出现在下发 payload 里。
- **分组与控件契约测试**：从 Schema 运行时节点断言五个分组的名称与顺序、以及单选/颜色/表格控件的 role，替代原先对源码文本的断言。

### 保留与删除

- **保留**：配置面板分组名与控件类型的断言（Schema 形状仍手写，它们是唯一守着面板渲染契约的断言），但读取方式从源码文本改为 Schema 运行时节点。
- **保留**：配置镜像 ref 初始值的行为断言（已有先例，规格照原值初始化即可存活）。
- **保留**：依赖具体配置值的运行时行为测试，例如撤回标记、character thinking 显示、协议选择。
- **删除**：锁死每个配置项整段 Schema 链式写法（含默认值字面量）的源码断言。
- **删除**：锁死下发 payload 逐条赋值语句、前端赋值语句写法的源码断言。
- **调整**：读取 `src/config.ts` 源文件路径的断言需要跟着文件切分调整；若断言内容已被上面的运行时断言覆盖，直接删掉而不是改路径。

### Prior art

- `tests/plugin.test.ts` — 插件 `apply` + 假 Koishi Console + 取入口回调 payload；已有一条断言下发 payload 完整对象的用例，可作为四端一致性测试的骨架。
- `tests/plugin-bot-probe.test.ts`、`tests/plugin-dispose.test.ts` — 内存 Console 替身与假 context 的写法；后者同时 import 服务端与前端两侧。
- `tests/webqq-members.test.ts` — 直接 import 前端配置镜像 module 断言 ref 初始值，是现成的行为测试范例。
- `tests/webqq-mock-environment.test.ts` — 含两条锁死 Schema 写法的源码断言，属于本次要替换的对象。

## Out of Scope

- **不生成 Schema 形状**。分组、字段顺序、控件 role、数值上下限、说明文案仍然手写。
- **不改任何配置项的名称、默认值或语义**，不新增也不删除配置项。
- **不改对外协议**：Console 事件名、数据库表名、浏览器本地存储 key、npm 包入口、插件名、构建入口一律不动。
- **不改 `Config` 的对外导出方式**。
- **不重构观察窗 SFC、实时消息流、OneBot 与模拟环境适配**。这些是架构评审里的候选 ② 到 ⑦，各自独立。
- **不引入前端 DOM 测试环境**。本 spec 的全部断言都不需要渲染组件。
- **不把构建产物检查加进单元测试**。「浏览器产物不含服务端依赖」放进第三批的人工验收清单，因为测试命令不依赖构建。
- **不新建前端跨领域共享 module**，配置镜像继续按领域归属分布。
- **不清理配置面板里已有的文案与分组划分**，即使其中存在可改进之处。

## Further Notes

### 验收清单

第一批与第三批各做一次完整验收；第二批不碰配置面板也不碰前端，只需构建加测试。

1. 完整构建。
2. 关闭旧主进程与相关子进程，确认端口释放，重启 Koishi，确认只有一个新实例且加载的是最新产物。
3. 在真实控制台里逐组核对五个分组：分组名、分组顺序、字段顺序、单选/颜色/表格控件、说明文案。
4. 实测至少三个开关真实生效：观察窗毛玻璃、消息发送栏、TIM 气泡小尖角。
5. 第三批额外确认前端产物里搜不到服务端依赖。
6. 浏览器验证结束后关闭本次任务打开的标签页与自动化进程，清理工具生成的临时目录。

### 相关 ADR

**ADR 0003** 已记录两个「下一个工程师会想改回去」的决策，实现时必须遵守：

1. 配置规格与 Schema 必须分文件，因为前端构建的 external 列表不含 koishi，规格一旦引用 koishi 就会被整包打进浏览器产物；合并这两个文件会静默引入这个回归，只能靠检查产物发现。
2. `Config` 不从配置规格派生，改用双向键集断言，因为它是对外导出类型，派生会让使用者的 IDE 提示退化。

**ADR 0001** 的外部兼容边界与前端禁止依赖规则同样适用，见上文「兼容边界」与「前端」两节。

### 新增领域术语

本 spec 使用的三个术语已写入词汇表：**配置规格**、**镜像配置项**、**配置镜像**。原有界面术语归入「界面」小节，内容未改。
