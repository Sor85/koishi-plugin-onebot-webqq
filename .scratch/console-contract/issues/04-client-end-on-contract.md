# 04 — 客户端接上控制台契约

**What to build:** 客户端这一端从类型到调用到守卫到浏览器全通。

现在客户端**完全没有类型**：发送与接收函数的事件名是纯字符串、载荷是 `unknown`，返回值靠调用点自己手转。所以写错名字、传错载荷、把返回值当成另一种东西用，三种错都要等到运行时——表现成「加载聊天历史失败」而日志里查不到原因。

载荷类型还各维护一份：服务端与客户端两份三百多行的类型文件，29 个同名类型字段全部一致，是两份手抄的副本；客户端另有一份第三份副本，缺了服务端接受的一个字段。

本票之后，客户端写错名字或载荷当场编译报错，载荷类型全仓只有一份，几十个消费方的 import 路径一处不动。

**Blocked by:** 02 — 控制台契约表与服务端两处声明。（不需要 03：广播端收类型是服务端那个方向，与本票并行。）

**Status:** ready-for-agent

**参考:** `.scratch/console-contract/spec.md` 的「两端如何接线」、「两处同类型不同名统一成服务端那份」、「客户端为什么保留门面而不是删掉」、「既有断言的保留与删除」、「import 图守卫」、「验收强度」；koishi-free 明线见 ADR 0003；本轮新立的那条 ADR 记着为什么不留兜底分支。

- [ ] 客户端的发送与接收函数按契约收类型；事件名、载荷、返回类型三者都被检查
- [ ] **重载不留字符串兜底分支。** 留了就等于没约束。撞上编译错误时回头看是哪一端的声明不对，不要加兜底
- [ ] 调用点手转返回值的写法跟着删掉——它们存在的唯一理由就是当时没有类型
- [ ] 客户端那三个类型文件改成从服务端 re-export 的门面，**文件留在原地**；几十个消费方的 import 路径一处不动
- [ ] 客户端专属的东西仍然住在那三个文件里（跨实例状态、配置镜像）
- [ ] 那份缺字段的第三份副本删掉，改用服务端那份（这是加字段，不会有消费方因此变红）
- [ ] 两处同一个类型两个名字的统一成服务端那份，**不在门面里做别名导出**——别名等于在类型层重造刚在事件名层消灭的「一个东西两个名字」
- [ ] 改名只动**类型**的出现处，同名的函数与变量不改
- [ ] 观察窗那个测试文件里锁**事件名**的源码文本断言删掉，接管者是本票的编译期约束
- [ ] 锁**模块位置**的那几条保留（观察窗不该自己接收广播、该由 store 接收）——契约管不了这个，删掉就没有接管者
- [ ] import 图守卫：从共享的那几个 module 出发做闭包，断言里面没有 koishi 边。读源码，**不读构建产物**（那要求先跑构建，做成「产物不存在就跳过」等于在最需要它的时候静默失效）
- [ ] 逐条失效实测：客户端事件名改一个字、载荷换成另一条请求的形状、返回值当成另一种类型用，三种都要编译失败；给共享 module 加一条 koishi 边 → import 图守卫红
- [ ] 人工核一次前端构建产物里没有 koishi
- [ ] 浏览器冒烟：打开观察窗确认联系人、历史消息、实时消息、小胶囊计数正常。**不做**完整真机验证（本轮零运行时改动，四步扇出一处没碰）
- [ ] 验证结束后按项目约定收尾（关闭本次开启的浏览器会话与自动化进程，清理工具生成的临时目录）
- [ ] 本轮没有任何行为改动，可见与不可见都没有
- [ ] `yarn typecheck`、`yarn test` 与 `yarn build` 通过
