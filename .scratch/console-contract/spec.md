# 控制台契约：事件名与载荷形状收成唯一权威声明

**Status:** ready-for-agent

**来源:** `/improve-codebase-architecture` 的候选 ⑦，经 `/grilling` 五轮定型。范围比报告原提议宽出一层，理由见下。相关决定：ADR 0003（配置规格与 koishi-free 明线，本轮第二次行使它）、ADR 0001（领域依赖方向与目标文件树）、本轮新立的一条 ADR（控制台契约表的位置与边界）。

## Problem Statement

控制台与插件之间有 24 个事件名：20 个请求（前端问、后端答）和 4 个广播（后端推、前端收）。每个名字现在要写 3 到 4 遍，而**没有任何一处能保证这几遍写的是同一个字符串**。

管理员看不到这条不变量，但它错了全是静默失效。请求名写错，前端拿到 `undefined`，界面显示「加载聊天历史失败」，日志里查不到原因。广播名写错更糟——完全静默，没有报错也没有失败提示，只是实时消息不再出现、小胶囊的计数停在旧值，看起来像机器人掉线了。

客户端那一端**完全没有类型**：发送函数的事件名是纯字符串，载荷是 `unknown`，返回值靠调用点自己手转。所以客户端写错名字、传错载荷、把返回值当成另一种东西用，三种错都要等到运行时。

比名字更重的一层是载荷类型：服务端与客户端各维护一份三百多行的类型文件，29 个同名类型字段全部一致——两份手抄的副本。手抄的痕迹已经留下了：同一条注释在两边被同义改写过。而且已经漂了一处，客户端另有一份第三份副本，缺了服务端接受的一个字段。

还有一处类型在对现实撒谎：小胶囊快照里的 Bot 列表，服务端声明的元素类型允许没有名字，客户端声明的要求必须有。查过唯一的生产者，它一定带名字——所以客户端那份才是对的，服务端在这个位置过松。反方向客户端漏抄了一个字段。

## Solution

一份**控制台契约**：24 个事件名连同各自的载荷与返回形状，只声明一次。

服务端两处声明从它派生，客户端的发送与接收函数按它约束，服务端的广播函数也按它约束。于是四端里任何一端漏改都编译失败，而不是等到运行时表现成「加载失败」或者干脆什么都不发生。

载荷类型跟着收成一份：客户端那三个类型文件改成门面，import 路径一处不动，两处同一个类型两个名字的统一成服务端那份。那处对现实撒谎的类型跟着改对。

管理员看到的东西一点不变。本轮零行为改动，可见与不可见都没有。

## Implementation Decisions

### 范围为什么与复查报告不同

报告把候选 ⑦ 定成「20 个 RPC、12 个一行转发、名字在三处维护」。核对后有一处漏报、一处低估、一处不成立，范围据此重划。

- **漏报了一处维护点。** 名字在**四处**写，不是三处：包入口的全局类型声明与插件上下文 module 的请求映射是两份独立的声明，前者是后者的超集——20 条请求逐字重复，另加 4 个广播名，那 4 个只在包入口出现。所以契约面是 24 个名字。
- **而且包入口那份在本仓库内没有任何消费者。** 注册侧的类型锚是插件上下文 module 的请求映射，客户端的发送函数来自本仓库自己写的类型垫片、事件名是纯字符串。两份声明漂移时零报错。这是最强的合并理由，报告没提。
- **低估了载荷层。** 真正的重复在载荷类型：服务端与客户端各一份三百多行的类型文件，29 个同名类型字段全部一致，差异只在一个联合类型别名用不用、以及注释在两边被同义改写。客户端另有一份第三份副本，缺了服务端接受的一个字段。这比名字值钱得多。
- **「12 个一行转发」实际是 13 个**，但这条收益本轮不取，理由见下。

### 契约表的形态与位置

**类型层，两个 interface。** 请求那 20 条与广播那 4 条各一个 interface，再导出两者的交集给包入口的全局声明用。方向就靠这两个 interface 表达，不靠签名形状推断，也不另立一个方向键 union——守卫要写「广播名必须有 broadcaster」这条判据，需要能直接拿到广播那一组的键集。

**不做运行时值表。** 配置规格是运行时值表，因为它要提供默认值；契约只提供名字与形状，做成值表就得给每条写一个占位值，那是把类型信息塞进值层。

**落在共享层，与控制台监听器门面并列。** 不放进 WebQQ 领域内部：契约同时管小胶囊的两个广播名，放进 WebQQ 会让那个领域拥有小胶囊的事件，撞上 ADR 0001 的依赖方向——和上一轮拒绝把消息落地扇出放进 WebQQ 是同一条理由。也不新开一个控制台目录：ADR 0001 明确解散过那个目录，重开会让那条迁移记录不再成立。也不能留在插件上下文 module：那个文件 type-import 了 koishi 与控制台包，客户端 import 它就越过 ADR 0003 那条明线——既有的两个共享 module 都只 type-import 零 koishi 的 module，没有一个碰过 koishi 本身。

### 名字数组为什么必须存在

类型层的 interface **在运行时没有键表可枚举**。而运行期恰好守着唯一无法编译期检查的失效形态：契约声明了但没人注册，今天完全静默。

所以契约 module 除类型外还导出一个只读的名字数组，并用一条编译期键集断言钉住「数组的元素集等于契约的键集」。运行期守卫读这个数组。

替代方案是让守卫测试自己维护一份 24 条清单——不行，那份清单漏一条时编译期抓不到，它不是契约的一端，而是第五份副本，正是本轮要消灭的东西。

### 两端如何接线

- 插件上下文 module 的请求映射改成等于契约的请求那一组，一行。
- 包入口的全局类型声明改成继承契约的交集，一行。
- 客户端类型垫片的发送与接收函数加基于契约的重载。垫片是本仓库自己写的、且 typecheck 用路径映射把控制台包**整体替换**成它，所以这不是模块增强、没有合并风险；文件里已有在声明块内 type-import 的先例。
- 服务端的广播函数一起收类型。它是这条缝上唯一还没类型的一端，成本是一行签名加上控制台监听器门面补泛型参数，4 个调用点一处不用动——它们的载荷类型早就在 koishi-free 的家里。

**重载不留字符串兜底分支。** 留了就等于没约束。真出现要发非契约事件的那天再加，判据是「有真实需求」而不是「怕编译不过」。这条要写进 ADR，因为下一个人撞上编译错误时的第一反应就是加那条兜底。

### 注册为什么不表驱动

13 个纯转发看着能收成「名字到 handler」的表加一个注册循环，但不做。

第一个理由软：那 6 个有实质逻辑的必须写成例外，而 13 个转发各自的参数类型标注是它们当前唯一的类型锚点。

第二个理由硬：表驱动会把名字表与 handler 实现焊在一起，而名字表要被客户端 import——一沾实现就把整条依赖链拖进浏览器产物，而且不报错，正是 ADR 0003 警告的那种静默后果。

这条和上一轮那个「实时消息合并有两个入口」是同一类误判：看着像重复，实际是正常复用。

### 唯一那个例外的注册点不搬

20 个请求里有一个注册在 WebQQ 装配 module 而不是常规的注册 module，因为它要用那里的两个局部函数（读机器人状态、广播机器人状态）。搬过去得把这两个注入进注册 module，注入面宽两项换来「20 个注册写在一起」的整齐，不值。

但它必须出现在契约里，而且守卫的注册端要**同时**覆盖两个 module——否则守卫会把唯一的例外漏掉，那正是这类断言最容易骗过自己的地方。

### 载荷类型搬家

4 条存储与缓存请求的载荷类型现在住在两个 koishi-tainted 的 module 里（它们 import 配置入口与数据库机件）。类型本身零 koishi 内容，只是住错了地方。

搬进 WebQQ 类型 module（零依赖），原文件改成 re-export——服务端二十个消费方一处不动。

不选「契约这 4 条改用客户端已有的声明」：方向反了，契约的权威会落在客户端。也不选「这 4 条只锁名字不锁类型」：会留下 4 个洞，而存储那两条恰好是载荷最容易漂的——客户端那份现在就是手抄的。

### 两处同类型不同名统一成服务端那份

有两个类型两端名字不同：会话摘要在客户端没有领域前缀、服务端有；小胶囊快照在客户端叫另一个名字。统一成服务端那份，**不在门面里做别名导出**。

别名等于在类型层重造我们刚在事件名层消灭的「一个东西两个名字」——将来有人在客户端 grep 服务端的类型名会一无所获，正是契约要消除的那种困惑。

成本比看上去小：会话摘要那个名字全仓出现二十多次，但大部分是同名的函数与变量（那些不改），真正的**类型**只出现 8 次、4 个文件；小胶囊快照那个 12 次、5 个文件。另外会话摘要是客户端那份类型文件里唯一没有领域前缀的类型——这本身就是它当初被临时加进去、而不是从服务端抄过来的证据。

### 客户端为什么保留门面而不是删掉

三个客户端类型文件（WebQQ 类型、机器人状态、小胶囊状态）改成从服务端 re-export，**文件留在原地**。

几十个消费方的 import 路径不动是这一票能塞进一个上下文窗口的全部原因。门面留在原地，客户端专属的东西也还有地方住——机器人那个文件里有跨实例状态，小胶囊那个里有配置镜像。

### 小胶囊广播载荷那处不健全的收窄

服务端声明的机器人列表元素类型允许没有名字，客户端声明的要求必须有。唯一的生产者一定带名字，所以客户端那份是对的。

**把服务端那个字段的元素类型换成机器人画像类型**，两端一致。不能直接把原来那个输入类型的名字字段收紧成必填——它还给消息输入路径用，那条路径上机器人确实可能没名字。换成机器人画像类型正好：它两端已经逐字一致、koishi-free，而且「小胶囊依赖 OneBot」是 ADR 0001 依赖图里认可的边，装配 module 已经在走这条边。

反方向客户端漏抄的那个会话字段由客户端补上——那是漏抄，不是故意收窄。

### 候选 ⑨ 折进来的边界

给广播函数收类型会波及三个实现控制台服务接口的测试替身，其中两个是候选 ⑨ 剩下的那对逐字重复的注册表型控制台替身。本轮无论如何都要动这三处。

**合并那对控制台替身**（改完再让下一轮回来改同样三处是纯浪费），**两个上下文替身不动**——它们能力确实不同，一个有定时器驱动、一个有 dispose 与带 warn 的日志器，合并会把参数面撑宽，那是候选 ⑨ 自己该判断的事，不该被本轮顺手决定掉。

### 新增领域术语

领域词汇表新开一节 `控制台`，一条：**控制台契约**——控制台与插件之间全部事件名及其载荷形状的唯一权威声明，含请求与广播两个方向。

不为「请求」「广播」各加一条：它们在这条定义里说清了就够，词汇表不该长成目录。

### 没有允许的行为改动

本轮全是类型层与 re-export。唯一的值层改动是类型垫片的重载与广播函数的签名，两者都不产生运行时代码。一处可见或不可见的行为改动都没有。

## Testing Decisions

### 什么算好测试

这一票的外部行为大部分落在**编译期**：四端里任一端漏改，`yarn typecheck` 必须失败。这不是「测实现细节」的例外——事件名与载荷形状对不上就是这条缝唯一会出的错，而编译期是它最高的接缝。

断言源码文本不算测行为。观察窗那个测试文件里锁事件名的十几条 `toContain` 是本轮要消灭的一类：它们证明得了「某个文件里有这行字」，证明不了「这个名字和后端注册的是同一个」。

### 接缝

一个新的，两个既有的。

1. **控制台契约 module 本身**（新建）。它同时是类型权威与运行期守卫的读取对象，落在这条缝的最高点——四端全部指向它。
2. **注册调用的记录**（既有）。运行期守卫读控制台替身记下的注册调用，这条路测试里已经用了多年。
3. **共享 module 的 import 图**（既有形态）。读源码做闭包，遍历方式在既有的命名空间守卫与排版守卫里都有先例。

客户端类型垫片不算第四个接缝——它是契约的消费方，被约束而不是提供约束。

### 编译期守卫（3 条）

- 插件上下文 module 的请求映射等于契约的请求组
- 包入口的全局声明继承契约的交集
- 名字数组的元素集等于契约的键集

机械是现成的：配置规格与配置 interface 之间的双向键集断言已经是同一套写法，本轮沿用。

### 运行期守卫（2 条）

- 契约声明的 20 条请求**全部**被注册，且注册端同时读常规注册 module 与 WebQQ 装配 module
- 契约声明的 4 条广播**全部**有 broadcaster

**每一端独立读取，不从契约派生两边。** 这是配置镜像那份四端守卫留下的教训——它的注释写得很直白：键集从 Schema 的运行时节点读而不是从规格自己读，从权威取键集会让断言变成同义反复。这里同理：注册那一端要从实际注册调用读，不能从契约的名字数组反推。

### import 图守卫（1 条）

从共享的那几个 module 出发做 import 闭包，断言里面没有 koishi 边。

ADR 0003 至今只有规矩没有守卫，而这条规矩被破坏时完全不报错——只能靠翻构建产物发现。本轮新增四条跨端 import 边，正好补上。

不做成读构建产物的断言：那要求 `yarn build` 先跑，`yarn test` 单跑时产物可能是旧的或干脆不存在；做成「不存在就跳过」等于在最需要它的时候静默失效，而本轮在消灭的正是这类断言。

### 既有断言的保留与删除

**删**：观察窗那个测试文件里锁事件名的那些源码文本断言。接管者是契约的编译期约束——名字写错不再编译。

**保留未动**：锁**模块位置**的那几条（观察窗不该自己接收广播、该由 store 接收）。契约管不了这个，删掉就没有接管者。真接口上的调用断言也全部保留——它们比对的是实际调用参数，本来就在真接缝上。

### 验收强度

`yarn typecheck` + `yarn test` + `yarn build`，加人工核一次前端构建产物里没有 koishi，再加**一次浏览器冒烟**：打开观察窗确认联系人、历史消息、实时消息、小胶囊计数正常。

不做完整真机验证。本轮零运行时改动，四步扇出一处没碰，那种量级的验证用在这里过重。但也不跳过浏览器：客户端那份类型文件变成纯类型 re-export 后会编译成空模块，rollup 处理这种情况是常规操作，但几十个消费方同时换 import 目标时，打开一次观察窗的成本不值得省。

### Prior art

双向键集断言在配置规格与配置 interface 之间已有一份。四端一致的运行期守卫在配置镜像那个测试文件里已有一份，连「不要从权威读键集」这条教训都写在注释里。源码遍历式守卫有两份（命名空间、排版）。查找注册调用的辅助函数在最大的那个测试文件里已经用了多处。本轮全部沿用，不新造形态。

## Out of Scope

- 把注册收成表驱动循环。会把名字表与实现焊在一起，而名字表要被客户端 import。
- 把那个唯一例外的注册点搬到常规位置。注入面宽两项换整齐，不值。
- 删掉客户端那三个类型文件、把几十个 import 重指到服务端。门面式 re-export 已经拿到全部收益。
- 合并候选 ⑨ 剩下的那两个上下文替身。它们能力不同，该由候选 ⑨ 自己判断。
- 给类型垫片的重载留字符串兜底分支。留了就等于没约束。
- 改动任何事件的名字、载荷形状或语义。本轮只让它们只声明一次。
- 客户端接收端的运行期守卫（断言 4 条广播都有 receiver）。其中两条已有既有覆盖，另外两条本轮由编译期约束兜住；新造一条会把接缝数从三个变成四个。
- 读构建产物的守卫。理由见 import 图守卫那节。
- 候选 ⑨ 的第三处重复（那个五行的内联替身）。够小，不该动。

## Further Notes

### 这一票为什么不拆成 expand–contract

客户端类型文件有几十个消费方，看起来像个宽 refactor。但门面式 re-export 让爆炸半径塌成三个文件——那三个文件自己就是 expand 与 contract 同时完成的地方。真正需要逐批迁移的情况不存在。

### 编译期守卫抓不到的那一格

契约声明了但没人注册，编译期抓不到——`addListener` 的类型参数只约束「你注册的名字必须在契约里」，不约束「契约里的名字你都得注册」。这一格由运行期守卫填。反方向（注册了但契约里没有）编译期就会红。

### 名字数组是本轮唯一的运行时足迹

契约本体是纯类型，运行时零成本。名字数组是唯一落到产物里的东西——一个字符串数组，且客户端不 import 它（客户端只要类型）。如果将来发现它真的进了浏览器产物，说明有人把它当运行时数据用了，那时要回头看是不是有了非守卫的消费者。

### 与候选 ⑨ 的边界

本轮只合并那对注册表型控制台替身，因为给广播收类型必须动它们。候选 ⑨ 剩下的量在这之后会更小，值不值得单独走一轮到时候重新估。
