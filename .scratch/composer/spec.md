# 输入区：从观察窗 SFC 里抽出可挂载可断言的 module

Status: ready-for-agent

来源：架构评审候选 ②（`/improve-codebase-architecture` → `/grilling` → `/prototype`），决策已全部收敛，DOM 能力已由抛弃型探针实测。约束见 ADR 0001、ADR 0002。

---

## Problem Statement

输入区的行为目前无法自动验证，只能靠人在浏览器里手点。

管理员遇到的症状是输入框层面的失灵：光标在插入提及后跳回开头、中文输入法上屏时丢字、`@` 菜单插到错误位置、粘贴进来的图片没被认成图片、切换会话后上一个会话选的附件还挂着——直接回车就发错人。这些都是「看起来能用、偶发出错」的一类问题。

维护者遇到的症状是每改一行输入区代码都要重新手动走一遍完整流程：输中文、插提及、粘图、切会话、回车发送。因为输入区的四百来行逻辑住在观察窗 SFC 里，只有一个 `visible` prop 作为对外接口，行为没有任何可调用的入口。

于是测试退化成了断言源码文本。现在有一批断言钉的是实现语句本身，例如「源码里必须出现某行取光标的调用」「源码里必须出现某个 base64 转换表达式」。这类断言的失败条件是「换了写法」而不是「行为错了」：重构会让它们全红，而真把光标算错却抓不住。

## Solution

把输入区做成一个可挂载的 module：草稿、光标往返、输入法、提及菜单、待发附件都搬进去，模板一并搬入，对外只留 props 与 emits。

管理员能观察到的变化有两处。一是切换会话时待发附件会随草稿一起清空，不再跨会话残留，消除误发。二是其余行为完全保持原样——输入、提及、粘贴、发送、发送区占位的表现都不变。

维护者能观察到的变化是：输入区的行为从此可以在无头 DOM 里挂载起来断言。挂载一次覆盖「渲染 + 事件绑定 + 逻辑」三层，因此「模板漏绑一个事件」这类过去只能靠手点发现的问题也进入了测试范围。发送不搬进输入区——它需要当前会话、回复目标、RPC 与错误文案，属于会话层。

## User Stories

### Koishi 管理员

1. 作为 Koishi 管理员，我希望在输入区打字时光标停在我刚输入的位置，这样我不用每敲几个字就重新点一次。
2. 作为 Koishi 管理员，我希望用中文输入法上屏时不丢字、不重复，这样我能正常说中文。
3. 作为 Koishi 管理员，我希望输入法候选窗开着的时候回车是上屏而不是发送消息，这样我不会把半句话发出去。
4. 作为 Koishi 管理员，我希望输入 `@` 时候选菜单出现在我输入的位置，选中后变成一个整体，这样我不会误删半个提及。
5. 作为 Koishi 管理员，我希望用方向键和回车就能选提及候选，不必换用鼠标。
6. 作为 Koishi 管理员，我希望按 Escape 关掉提及菜单而不是关掉整个输入区。
7. 作为 Koishi 管理员，我希望从消息右键菜单点「提及」时，提及被插进当前草稿而不是另起一行。
8. 作为 Koishi 管理员，我希望在私聊里不出现提及菜单，因为那里没有群成员可提。
9. 作为 Koishi 管理员，我希望删除一个提及是一次删掉整块，而不是留下半个名字。
10. 作为 Koishi 管理员，我希望粘贴截图时它被当作图片附件，而不是变成一串乱码文字。
11. 作为 Koishi 管理员，我希望粘贴文字时正常插入文字，不被附件逻辑吃掉。
12. 作为 Koishi 管理员，我希望选中的图片、视频、文件在发送前有预览缩略图，这样我能确认选对了。

14. 作为 Koishi 管理员，我希望点击待发图片能放大看清，避免发错图。
15. 作为 Koishi 管理员，我希望**切换会话时上一个会话选的附件被清掉**，这样我不会把图片误发给另一个人。
16. 作为 Koishi 管理员，我希望切换会话时草稿也被清掉，保持现有行为不变。
17. 作为 Koishi 管理员，我希望草稿为空且没有附件时发送按钮不可用，避免发出空消息。

20. 作为 Koishi 管理员，我希望附件预览出现时消息列表底部同样让出空间。
21. 作为 Koishi 管理员，我希望关闭消息发送功能时输入区整块消失，界面不留空壳。
22. 作为 Koishi 管理员，我希望进入多选模式时输入区让位给多选操作栏。
23. 作为 Koishi 管理员，我希望输入区的外观、间距、毛玻璃表现在这次改造前后完全一致。
24. 作为 Koishi 管理员，我希望输入区内容超长时能正常滚动，自定义滚动条照常工作。
25. 作为 Koishi 管理员，我希望输入区在 Chrome 和 Firefox 下表现一致。

### 插件维护者

32. 作为插件维护者，我希望输入区不认识群成员领域，候选列表由调用方传入，这样它在私聊、群聊和将来任何场景下形状一致。
33. 作为插件维护者，我希望发送不进输入区，因为发送需要会话、回复目标、RPC 和错误文案，塞进去会让接口长出一串会话参数。
34. 作为插件维护者，我希望输入区自己观测高度并只对外给一个数字，而不是把两个 DOM 引用暴露出去让别人来量。
35. 作为插件维护者，我希望草稿 token 那层纯函数继续留着自己的测试，但新增的行为断言一律打输入区接口。
36. 作为插件维护者，我希望 DOM 测试环境只对需要的测试文件生效，不改变其余几十个无关测试的运行条件。
37. 作为插件维护者，我希望观察窗 SFC 因此明显变短，找输入区代码时不必在两千行里翻。
38. 作为插件维护者，我希望输入区搬迁后浮层挂载方式不变，不触碰既有的 Teleport 与毛玻璃约束。
39. 作为插件维护者，我希望这次改造不改变任何对外协议与配置项。

### 接手实现的 agent

## Implementation Decisions

### 输入区 module 的形态

- 做成**一个 Vue 组件**，模板一并搬入，对外只有 props 与 emits。不做 composable：那样测试得自己造一个可编辑元素、自己把事件绑上去，测试里那套绑定不是生产在用的那套，「模板漏绑一个事件」仍然测不出来，接缝停在半空。
- 也不做「注入编辑器端口 + 内存假编辑器」：生产只有一种可编辑元素，端口不是为了变化而存在，只为绕开测试环境；而假编辑器编码的是我们对 DOM 的假设，真实 bug 恰恰长在假设不准的地方。

### 边界：什么进，什么不进

进输入区：草稿与 token、可编辑区渲染、光标往返、输入法 composition、提及菜单、待发附件（类型判定、粘贴、预览、移除、转成发送元素）、发送区占位的观测。

不进输入区：

- **发送动作**。它依赖当前会话、回复目标、发送 RPC、共用的错误文案 ref、发送锁与发送后重新聚焦——都是会话层知识。输入区负责产出可发送内容并在成功后清空，实际发送由调用方完成。
- **提及候选的来源**。候选由调用方作为输入传入；输入区只做匹配与菜单状态。输入区一旦认识「群成员」，接口就要长出群 ID 与成员刷新时机。
- **是否渲染输入区的门禁**。发送功能开关与多选模式决定输入区整块是否存在，判断留在父层；否则输入区要认识「多选模式」这个会话状态。
- **图片放大浮层**。点击待发图片时输入区只发出请求，由观察窗决定用哪个浮层，避免输入区认识二级面。

### 发送区占位

输入区自己观测自身高度，对外只暴露一个数字。此前的判断是「消费方是消息列表所以归工作区」，那是把「谁消费」和「谁知道」混为一谈：消息列表消费这个数字，但只有输入区知道自己什么时候变高。把观测藏在实现里、只暴露一个数，接口更小。

### 行为修正

**切换会话时同时清空待发附件。** 现状是切会话清草稿、清提及菜单、清回复目标，但不清附件——附件只在发送成功和组件卸载时清。这会让上一个会话选的图片跟着进入新会话，回车即误发。输入区一旦同时持有草稿与附件，「切会话时清什么」就成了它接口的一部分（生命周期与顺序约束属于接口），把这处不一致原样搬进新 module 等于把它固化成新接口的语义。

除此之外不改任何行为。

### 草稿 token 层

已抽出的草稿 token 纯函数层保留为输入区的**内部实现**，它自己的测试继续留着。深 module 内部允许有内部接缝，不必为了「接口是唯一测试面」删掉稳定且便宜的纯函数测试。但立一条规矩：新增的输入区行为断言一律打输入区接口，否则会重演「叶子测得很细、bug 在调用处」——那正是本候选要修的病。

### 测试环境

- 引入 happy-dom 与 Vue 组件测试工具两个开发期依赖，精确版本。
- **按测试文件开启** DOM 环境，其余文件保持默认的 node 环境。理由有二：现有测试在 node 环境下跑得很快，全局挂 DOM 要给每个文件付一次环境搭建成本；前端有五处把状态挂在全局对象上的 module 与直接摸 document 的 module，全局切换等于改变几十个无关测试的运行条件。
- 测试运行器默认每个测试文件独立进程，因此 DOM 文件与 node 文件互不影响，全局单例不会串。

### 探针实测得到的两条限制（会影响验收判据，不影响接口形状）

抛弃型探针在 happy-dom 下验证了光标往返、可编辑区渲染、从 DOM 反读草稿、输入事件、粘贴携带文件、文件转字节、对象 URL、以及**真实 SFC 的挂载**（模板绑定、emits、props 驱动渲染、输入法状态反映到渲染、内部 ref 暴露均正常）。光标契约被证实可原样往返：

```
setCaret(编辑器, tokenIndex=2, offset=3) → getCaret(编辑器) === { tokenIndex: 2, offset: 3 }
```

两条限制：

1. **尺寸观测回调在无头 DOM 里永不触发**（无布局引擎），且取矩形恒返回 0 —— 但可以直接覆写打桩。因此发送区占位只能**打桩测公式**：断言「给定上下文层高度，占位数字应为多少」，而不是「改了样式后数字自己变了」。
2. **输入法事件的 data 字段在无头 DOM 里丢失**。生产代码目前不读它，因此不影响；但由此产生一条约束——**输入区不得开始依赖输入法事件的 data 字段**，否则该行为将失去测试面。

未测另一套 DOM 实现：happy-dom 已清掉全部要求，另一套回答不了任何还开着的问题。

### 兼容边界

- 不改配置项、Console 事件名、数据库表名、浏览器本地存储 key。
- 搬迁模板时保持既有的浮层挂载方式与毛玻璃约束不变（ADR 0002），不把提及菜单换成别的挂载路径。
- 自定义滚动条指令仍挂在真实 DOM 元素上，不挂在可能返回 Fragment 或注释节点的组件上。
- 不新建被两个前端领域共同依赖的 module（ADR 0001）。

## Testing Decisions

### 什么算好测试

只断言外部可观察的行为：挂载后的渲染结果、DOM 交互引发的 emits、以及交互后从可编辑区能读回什么。不断言源码里出现过哪些字符串，也不断言内部函数被怎么调用。

判据是：把实现换一种写法而行为不变时，测试必须仍然通过。现存的输入区断言大多不满足这一条——它们钉的是实现语句，因此重构必定全红，而红的原因是重构成功。

### 接缝

**一个外部接缝：挂载输入区组件。** 断言全部打在这里——传 props、改可编辑区的 DOM、派发真实事件、读 emits 与渲染结果。这是可达的最高接缝：一次挂载同时覆盖渲染、事件绑定与逻辑三层。探针已实测这条路可行。

**一个既存的内部接缝：草稿 token 纯函数层。** 保留，其现有测试不动。不通过它新增行为断言。

**不新增任何其它接缝，不为可测性新增导出。** 提及候选与发送都经 props/emits 跨接缝传递，因此测试不需要摸输入区内部。

### 要测的行为

- **草稿与光标**：渲染 token 后设置光标再读回，位置一致；在提及之后的文字 token 内定位；插入提及后光标落在提及之后。
- **提及**：输入 `@` 后菜单开启并带上查询串；方向键改变选中项；回车与 Tab 选中候选并把它变成一个原子 token；Escape 只关菜单；私聊场景不开菜单；从外部请求插入提及时进入同一份草稿。
- **输入法**：composition 期间回车不触发发送；composition 结束后草稿与光标同步；composition 期间不弹提及菜单。
- **待发附件**：按 MIME 与扩展名判定图片/视频/文件三类；粘贴带文件时阻止默认行为并收下文件；移除单个附件；请求放大预览时发出事件而不自行开浮层；附件转成发送元素时字节正确。
- **可发送判定**：草稿空且无附件时不可发送；只有附件时可发送。
- **切换会话**：草稿、提及菜单、回复目标、**待发附件**全部清空。
- **发送区占位**：打桩给定上下文层高度，断言对外输出的数字；回复条或附件出现/消失时数字随之变化。
- **门禁**：父层不渲染输入区时，输入区完全不存在（这条断言在父层）。

### 保留与删除

- **删除**：钉实现语句的断言，包括取光标的调用写法、base64 转换表达式、对象 URL 调用、占位高度计算式、文件类型判定的具体分支写法。每删一条要能指出接管它的行为断言。
- **删除**：钉模板结构字符串的断言（某个 ref 名、某个事件绑定写法）。改由挂载后的渲染与交互断言接管——断言 DOM 上确实存在可编辑区、确实响应粘贴，比断言源码里有这个字符串强。
- **保留**：锁样式契约的断言（提及菜单不产生内部滚动条、回复条与附件共用上下文层的换行与行高）。它们守的是视觉契约，不是输入区逻辑，属于另一个候选的范围。
- **保留**：草稿 token 纯函数层的现有测试。
- **保留**：与输入区无关的消息气泡、群成员菜单等断言，即使它们文案里出现「提及」。

### Prior art

- 仓库此前完成的一轮配置重构里，已经实践过「删源码文本断言时逐条指出接管者」这条纪律，可照同样方式记录。
- 直接 import 前端 module 并断言其导出值的测试已有先例，可作为组件测试之外的补充读取点。
- 测试运行器已在用的按文件指定环境的注释写法已实测可用，默认环境为 node。

## Out of Scope

- **不改发送逻辑**。发送仍由会话层完成，包括发送 RPC、错误文案、发送锁与发送后聚焦。
- **不改输入区的外观**。间距、类名、毛玻璃表现、滚动条方案一律保持，样式契约断言不动。
- **不改提及候选的数据来源**。候选仍来自群资料，只是改为由调用方传入。
- **不引入全局 DOM 测试环境**，不改动与输入区无关的测试的运行条件。
- **不重构观察窗 SFC 的其它部分**——会话内查找、二级面栈、多选转发、窗口缩放都是架构评审里的其它候选。
- **不改对外协议**：配置项、Console 事件名、数据库表名、浏览器本地存储 key 一律不动。
- **不改浮层挂载方式**，不触碰 ADR 0002 关于毛玻璃采样边界的决策。
- **不为输入区新增功能**：不加富文本、不加草稿持久化、不加多会话草稿保留。
- **不处理跨浏览器的真实输入法差异**，无头 DOM 只能覆盖代码自己的处理逻辑，真机输入法验证仍靠人工。

## Further Notes

### 验收清单

1. 完整构建。
2. 关闭旧主进程与相关子进程，确认端口释放，重启 Koishi，确认只有一个新实例且加载的是最新产物。
3. 在真实浏览器里人工走一遍无头 DOM 覆盖不到的部分：中文输入法连续上屏、真实截图粘贴、真实文件选择、发送成功后焦点回到输入框。
4. 验证切换会话后待发附件确实被清空。
5. 验证回复条与附件预览出现时，消息列表底部让出的空间正确、气泡不被压住。
6. 验证输入区在 Chrome 与 Firefox 下布局与滚动一致。
7. 验证关闭消息发送功能与进入多选模式时输入区整块消失。
8. 浏览器验证结束后关闭本次打开的标签页与自动化进程，清理工具生成的临时目录。

### 开发期依赖

本 spec 需要两个新的开发期依赖：一套无头 DOM 实现与一套 Vue 组件测试工具，均以精确版本引入。它们已在探针阶段装入工作区并实测通过；实现时若发现被回退，需要重新加回。安装时会出现一条编译器 peer 依赖未提供的告警，实测不影响 SFC 挂载——只有在测试里写模板字符串才会撞到它。

### 新增领域术语

本 spec 使用的四个术语已写入词汇表：**输入区**、**草稿**、**待发附件**、**发送区占位**。其中「发送区占位」此前没有名字，是这次把高度观测收进输入区后必须命名的概念。

### 探针的留存

DOM 能力探针是抛弃型代码，已在得到结论后删除，结论记录在本 spec 的 Implementation Decisions 里。探针代码本身未留档——按项目规则未经明确要求不新建分支、不提交。若日后需要复现，按 Implementation Decisions 里那份能力清单重写即可，成本约十几分钟。
