# 04 — 待发附件的挂载式断言

**What to build:** 待发附件的行为从此可自动验证。目前「粘贴截图有没有被认成图片」「粘贴纯文字会不会被附件逻辑吃掉」「附件转字节对不对」只能靠人手点，而其中一条错了就是发出去的内容不对。本 ticket 把这些变成挂载式断言，并删掉对应的源码文本断言。

**Blocked by:** 02 — 输入区组件搬迁与草稿光标断言。

**Status:** resolved

**参考:** `.scratch/composer/spec.md` 的 Testing Decisions「要测的行为」一节。

- [x] 挂载式断言覆盖：按 MIME 与扩展名判定图片、视频、文件三类
- [x] 粘贴带文件时阻止默认行为并收下文件
- [x] 粘贴纯文字时正常插入文字，不被附件逻辑吃掉
- [x] 可以移除单个待发附件，且释放其预览资源

## Comments

- 落在 `tests/webqq-composer-attachments.test.ts`（14 条）：三类判定、无 MIME 时的扩展名白名单回退、视频缩略图只取首帧且不可点击放大、粘贴带文件拦默认行为、粘贴纯文字不拦也不产生附件、文件选择按钮走同一份待发附件、移除单个附件并释放预览资源、放大只发对外事件、卸载释放全部预览资源、只有附件也能发送、字节与 MIME 前缀正确、草稿文字排在附件之前、发送成功后清空。
- 判定 MIME 的断言用 `clip.mkv` + `video/x-matroska`：扩展名不在可播放白名单里，只有 MIME 分支能把它认成视频。第一版用了 `clip.mp4` + `video/mp4`，删掉 MIME 分支后扩展名回退照样得到 `video`，改坏了也不变红——换成 mkv 后失效实测才成立。
- 字节断言是真的解码回来比对：`data` 前缀必须是 `data:image/png;base64`，`base64` 段解码后等于原始字节数组；没有 MIME 时前缀退回 `data:application/octet-stream;base64`。测试里 `@koishijs/client` 的替身用 `Buffer` 实现 `Binary.toBase64`，所以断言检查的是生产侧「读文件 → 编码 → 拼前缀」这条链，而不是替身本身。
- 预览资源的释放用 `vi.spyOn(URL, 'revokeObjectURL')` 断言实参等于该附件的 `src`，因此「revoke 了但 revoke 错了对象」也能抓到。
- 失效实测（改坏→变红→改回）：删掉视频 MIME 分支、把扩展名白名单放宽成「有扩展名就算视频」、粘贴不再 `preventDefault`、移除时不 revoke、字节改成编码文件名、放大按钮不发事件——六条都变红。
