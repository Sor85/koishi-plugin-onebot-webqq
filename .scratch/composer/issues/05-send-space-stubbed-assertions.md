# 05 — 发送区占位的打桩断言

**What to build:** 发送区占位从此可自动验证。管理员看到的表现是回复条或待发附件出现时，消息列表底部让出正确的空间、气泡不被压住；这个数字算错就会压住最后一条消息。本 ticket 用打桩把它变成断言，并删掉锁占位计算式的源码断言。

**Blocked by:** 02 — 输入区组件搬迁与草稿光标断言。

**Status:** resolved

**参考:** `.scratch/composer/spec.md` 的「探针实测得到的两条限制」一节。

已实测的限制：无头 DOM 没有布局引擎，尺寸观测回调**永不触发**，取矩形恒返回 0，但可以直接覆写打桩。因此本 ticket 的断言只能是「给定上下文层高度，占位数字应为多少」，不能是「改了样式后数字自己变了」。

- [x] 打桩给定上下文层高度后，断言输入区对外输出的占位数字
- [x] 回复条出现与消失时，占位数字随之变化
- [x] 待发附件出现与消失时，占位数字随之变化
- [x] 多选模式下占位取固定值这条断言落在父层（门禁在父层，输入区不认识多选模式）
- [x] 断言不依赖真实布局，也不依赖尺寸观测回调被触发
- [x] 锁占位计算式的源码文本断言已删除
- [x] 实测：故意改错占位公式时断言失败
- [x] 全量测试通过

## Comments

- 落在 `tests/webqq-composer-send-space.test.ts`（5 条）。打桩方式是覆写 `Element.prototype.getBoundingClientRect`，按选择器给出各层高度，因此断言完全不依赖布局引擎，也不依赖尺寸观测回调被触发。
- 断言的就是公式：只有发送控件时 `44 + 28`；回复条出现时 `44 + 40 + 8 + 28`，消失后退回 `44 + 28`；附件出现与移除同理；回复条与附件同时存在时上下文层只有一个、只计一次高度。
- 另有一条断言「发送控件高度只作为 CSS 变量挂在 form 上」，同时确认对外没有第二个数字（没有 `update:sendHeight` 这类事件）。
- 多选模式那条留在父层：`tests/webqq-view.test.ts` 保留 `'--onebot-webqq-webqq-send-space': ${selectionMode.value ? 64 : webQQSendSpace.value}px` 这一条源码断言。它锁的不是占位计算式（计算式已经改由打桩断言接管），而是「门禁在父层、输入区不认识多选模式」这个边界；观察窗 SFC 挂不起来，没有运行时替代读取点。
- 失效实测（改坏→变红→改回）：把公式里的 `+ 28` 去掉、把上下文层的 `+ 8` 去掉——两条都变红。
