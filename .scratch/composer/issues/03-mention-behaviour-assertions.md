# 03 — 提及的挂载式断言

**What to build:** 提及行为从此可自动验证。目前这些场景只能靠人在浏览器里逐个手点：输入 `@` 后菜单该不该开、键盘选中后是否变成一个整体、按 Escape 会不会误关整个输入区、私聊里会不会冒出菜单。本 ticket 把它们变成挂载式断言，并删掉对应的源码文本断言。

**Blocked by:** 02 — 输入区组件搬迁与草稿光标断言。

**Status:** resolved

**参考:** `.scratch/composer/spec.md` 的 Testing Decisions「要测的行为」一节。

- [x] 挂载式断言覆盖：输入 `@` 后菜单开启并带上查询串
- [x] 方向键改变选中项；回车与 Tab 选中候选并把它变成一个原子 token
- [x] Escape 只关提及菜单，不影响草稿与其它状态
- [x] 未传入候选（私聊场景）时菜单不开启
- [x] 输入法进行中不弹提及菜单
- [x] 外部请求插入提及时进入同一份草稿，不另起一行
- [x] 删除一个提及是整块删除，不留下半个名字
- [x] 对应的源码文本断言已删除，删掉的每一条都能指出接管它的行为断言
- [x] 逐条实测：故意改坏任一条提及行为时，对应断言失败
- [x] 全量测试通过

## Comments

- 落在 `tests/webqq-composer-mention.test.ts`（14 条）：菜单开启与查询串筛选、群名片关键字命中、已有文字后面键入 `@`、input 早于光标更新时下一微任务补开菜单、方向键循环、回车与 Tab 选中成原子 token、鼠标 `mouseenter`/`mousedown`、Escape 只关菜单、私聊不开菜单、外部请求插进同一份草稿且不另起一行、同一成员连续插入两次、提及节点 `contenteditable="false"`、整块消失后草稿无残留。
- 「输入法进行中不弹提及菜单」放在 `tests/webqq-composer-editor.test.ts` 的输入法 describe 里，和「输入法进行中回车不发送」成对，读起来更完整。
- 「删除一个提及是整块删除」拆成两条断言：一条锁渲染形态（提及是 `contenteditable="false"` 的原子节点，浏览器因此按一个字符删），一条锁读回（节点整块消失后草稿里只剩另一个提及、文本里不含被删的名字）。原生删除动作本身是浏览器行为，无头 DOM 覆盖不到，留给人工回归。
- 失效实测（改坏→变红→改回）：Escape 分支顺带清草稿、Tab 不再走选中路径、`nextTick` 补读改成同步执行、外部提及请求不回收——四条都变红。
- 「私聊不开菜单」有两道独立守卫（`updateMentionMenuFromDraft` 的候选数判断与 `mentionMenuOpen` 的候选数判断），只改坏一道时行为不变、断言照过；两道一起改坏才变红。两道都保留：一道拦状态写入，一道拦渲染。
