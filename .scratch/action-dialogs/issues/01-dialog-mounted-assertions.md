# 01 — 两个对话框的挂载式断言

**What to build:** 管理员做需要征询的操作时，两类对话框的行为从此可自动验证。目前「删好友失败后对话框留在原地」「处理期间两个按钮禁用、文案变处理中」「连点不会重复发出破坏性动作」「上次失败后重开不卡在处理中」「打开时输入框预填当前值」这些全靠人手点，而其中任何一条坏掉都直接伤到用户：要么以为删成功了，要么把人踢两次。本 ticket 把它们变成挂载式断言。

两个对话框本来就是纯 props/emits，不需要任何改造就能挂。**生产代码零改动。**

顺带给共用 Dialog 的挂载路径立第一条运行时守卫：遮罩与内容必须同时存在。项目的生产兼容规则要防的正是「遮罩在、内容退化成注释节点」这种形态，而现在只有源码文本守着——那种守法抓不到挂载路径退化。

**Blocked by:** 无 — 可以立即开工。

**Status:** resolved

**参考:** `.scratch/action-dialogs/spec.md` 的 Testing Decisions；两套协议为什么不合并见 ADR 0007；浮层挂载约束见 ADR 0002。挂载脚手架的范本是输入区与查找页那几个测试文件。

已知的挂载准备：Dialog 内容层在模块作用域链到控制台客户端的颜色模式钩子（经 WebQQ 设置模块），替身必须连它一起 mock，不只是代理地址函数。无头 DOM 没有 Popover API，但浮层提升工具本来就守了这个判断并静默返回，不妨碍挂载。

## Comments

落地位置：`tests/webqq-action-dialog-views.test.ts`（15 条断言，按文件开 happy-dom）与 `tests/helpers/webqq-action-dialogs.ts`（挂载脚手架）。内容被 `Teleport` 到 body，所以脚手架统一按文档查 `[data-slot="dialog-overlay"]` 与 `[data-slot="dialog-content"]`，`dialogLayers()` 一次返回两者的在场情况——遮罩与内容「同时存在」这条守卫因此断言的是一对布尔，而不是只看其中一个。

两条断言的写法值得记一笔：

- **不双提交**走同一轮内的两次 `element.click()`。等一次 nextTick 再点，按钮上已经打了 `disabled`，无头 DOM 未必替真实浏览器拦住派发；同轮连点时 DOM 还没打上 `disabled`，拦住第二次的只有组件自己的提交态判断。
- **重开重置提交态**用一个宿主一次都不回话的确认请求把提交态留在「处理中...」，再关一次开一次。这样去掉打开时的重置 watch 才会变红——失败路径的 `finally` 本来就会放下提交态，拿失败来测这条会自证通过。

逐条失效实测跑了 18 处改坏，全部有对应断言变红。其中两处一开始没红，都不是断言问题：

- `@click.self` 改成 `@click` 单独不足以让「点内容不关」变红，因为内容那层的 `@click.stop` 会先截住冒泡。两者是互为冗余的两道防线，同时拆掉才红。
- 把 `try/catch` 换成语法不合法的形态时构建直接失败，改成 `catch (error) { throw error }` 这种合法改坏后，「不产生未处理的 promise rejection」如期变红。
