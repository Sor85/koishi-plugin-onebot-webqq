# 02 — 对话框编排收成 module

**What to build:** 两类对话框的编排从此可自动验证，提交回调不再是一个活在模块级可变量里的东西。目前一级工作区把 16 个状态名平铺给模板，其中两个是模块级的 `let submit`——它们不在响应式系统里，而且在取消、Escape、点遮罩这三条关闭路径上根本不清，只靠下一次打开覆写才没出事。编排里那句「操作已失效」的拒绝分支就是这套设计逼出来的补丁。

核心形状是**提交回调作为 spec 对象的一个字段**，spec 整体是一个可空引用：于是「对话框开着」与「提交回调在场」变成同一个事实，两个可变量与独立的开关布尔一并消失，三条关闭路径自动清掉回调，那句补丁守卫连可达路径都没有。

管理员看到的界面与交互不变。唯一的行为改动（关闭时清回调）不可见——现在的泄漏被下一次打开覆写掩掉了。

**Blocked by:** 无 — 可以立即开工。**但建议排在 01 之后**：01 生产代码零改动，是零风险的安全网；本票搬迁时最容易犯的错就是把两个对话框的完成顺序写成同一个（一个先关后跑、一个跑完再关），有 01 的断言兜着能立刻发现。

**Status:** resolved — 除「删好友描述接管断言」一条外全部达成，该条的结论与两条后续选项见 Comments

**参考:** `.scratch/action-dialogs/spec.md` 的 Implementation Decisions 与 Testing Decisions；两套协议不合并、也不收成 Escape 栈的理由见 ADR 0007；模块形态的判据见 ADR 0004。编排测试的范本是通知菜单那条断言（注入假实现、事件序列断言）。

## Comments

落地位置：`client/webqq/stores/webqq-action-dialogs.ts`（`useWebQQActionDialogs`）与 `tests/webqq-action-dialogs.test.ts`（11 条断言，跑在默认 node 环境）。

形状按票走：提交回调是 spec 的字段，两个开关是带 setter 的计算值，置为关闭就清 spec。观察窗那 12 个声明换成一次解构，`openActionDialog` / `openConfirmDialog` / `confirmActionDialog` / `confirmDestructiveAction` 四个名字一个都没改，六个调用点各自只改了 `onConfirm:` → `submit:` 这一个 token。生产代码净减 78 行、增 26 行。

两处实现决定与票面文字有出入，都是往简的方向：

- 两个 open 函数直接把 spec 存下，不再在编排里补默认值。原先的 `input.confirmText || '保存'` 与组件自己的 `confirmText: '保存'` 是同一个默认值写了两遍；spec 的可选字段透传成 `undefined` 后由组件的 props 默认值兜，行为逐字等价，默认值只剩一处。
- 提交路径统一写成 `Promise.resolve(spec?.submit(...))`。可选链正好接住「spec 不在场」这个不可达分支，于是不需要任何形式的守卫语句，也就没有把「操作已失效」换个写法留下来。

失效实测跑了 13 处改坏，12 处有对应断言变红。唯一没红的是**把「操作已失效」守卫原样补回来**——它落在不可达分支上，行为断言按定义抓不到。这正是票里那条要求成立的证据（守卫没有可达路径），而不是断言有缺口；如果哪天它变得可达，说明 spec 形状退化了，届时该看的是形状。

删好友描述那条要求**没有达成**，两位复查者独立指出同一件事，记录如下。

票面要求把锁模板字面量的 `toContain` 删掉，接管者是行为断言「请求删除好友时，确认对话框的描述为『确定删除好友「Alice」？』」。前半做到了，后半做不到：那句描述由观察窗的 `confirmDeleteFriend` 拼出，而本轮的两个接缝——两个对话框的挂载面与编排的 options 对象——都观测不到它。挂载断言里那句 `expect(dialogDescriptionText()).toBe('确定删除好友「Alice」？')` 读的是脚手架自己传进去的 props，观察窗改成别的措辞它照样绿。

第一版实现按票面把断言整条删了，只留 `not.toContain`，于是这句措辞一度没有任何守卫。现在退回一条**只锁文案片段**的源码断言 `expect(webqqView).toContain('确定删除好友「')`：它守的是用户看得见的措辞，不是实现语句，换插值写法或改 fallback 都不会误报——票面反对的是后者（「等价改写会误报，改坏行为反而可能照过」），这一条不落在那个反对里。

要真正拿到票面写的那种行为断言，只有两条路，都超出本票范围，留给下一次决定：

- 把六个对话框的措辞从观察窗搬进纯函数（`utils/` 里的 view 层），各自直接断言。代价是新增一层，而且只为其中一句搬会让另外五句形态不一致——要做就六句一起。
- 给观察窗本身立挂载接缝。它从来没被挂载过，替身面很大（控制台 RPC、存储、api module 全要 mock），本票的 Testing Decisions 明确写了「不新造接缝」。
