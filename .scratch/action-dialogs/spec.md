# 二级面对话框：编排收成 module，两套协议各自留守

**Status:** ready-for-agent

**来源:** `/improve-codebase-architecture` 的候选 ④，经 `/grilling` 三轮定型。范围与报告原提议有实质差异，理由见下。相关决定：ADR 0007（两套完成协议不合并）、ADR 0002（浮层挂载约束）、ADR 0004（对照：什么时候才该做成组件）。

## Problem Statement

管理员在 WebQQ 里做需要征询的操作，都会弹出一个二级面：设好友备注、改群名片、设专属头衔走**输入对话框**；删好友、踢出群组走**确认对话框**。这两条路径现在没有任何自动化守卫，几类失败形态只靠人手点：

- 删好友失败时对话框应该留在原地供重试，而不是关掉让人以为成功了。
- 处理期间两个按钮都该禁用、确认按钮显示「处理中...」，否则连点会重复发出破坏性动作。
- 上一次失败后重新打开，不能还卡在「处理中...」。
- 打开输入对话框时输入框应该预填当前值，重开要刷新成最新值。

维护者这一侧的问题更具体。两个对话框的编排把 16 个状态名平铺给模板，其中两个是模块级的 `let submit`——它们不在响应式系统里，而且在取消、Escape、点遮罩这三条关闭路径上**根本不清**，只靠下一次打开覆写才没出事。编排里那句 `if (!submit) reject(...)` 就是这套设计逼出来的补丁。`'操作失败'` 这句 fallback 写了两遍。整条路径上只有 2 条源码文本断言，其中一条锁的还是删好友确认文案的模板字面量。

## Solution

分两块，都不改界面。

第一块是给两个对话框组件立挂载式断言。它们本来就是纯 props/emits，不需要任何改造就能挂，于是「失败保持打开」「处理中禁用」「不双提交」「重开重置提交态」这些真逻辑第一次有守卫。顺带给共用 Dialog 的挂载路径加一条运行时守卫：遮罩与内容必须同时存在。

第二块是把编排收进一个 module。关键形状是**提交回调塞进 spec 对象**，spec 整体是一个可空的引用：于是「对话框开着」与「提交回调在场」变成同一个事实，两个模块级 `let` 一起消失，独立的开关布尔不再需要，取消时回调自动清掉，那句补丁守卫连存在的理由都没有。共享的错误落点与回调生命周期收进一处，`'操作失败'` 从两处变一处。

两套完成协议都保留，留在各自的组件里（ADR 0007）。

## User Stories

### Koishi 管理员

1. 作为管理员，我想给好友设备注时看到当前备注已经填在输入框里，这样我改的是现有值而不是从零重打。
2. 作为管理员，我想改群名片时看到当前名片已经填好，理由同上。
3. 作为管理员，我想设专属头衔时看到当前头衔已经填好，理由同上。
4. 作为管理员，我想在输入框里直接按回车提交，这样不用移到确认按钮。
5. 作为管理员，我想点取消就什么都不发生，这样我能安全地退出。
6. 作为管理员，我想按 Escape 关掉对话框，这样键盘操作是连贯的。
7. 作为管理员，我想点对话框外面的遮罩就关掉它，这样退出方式和其他浮层一致。
8. 作为管理员，我想点对话框内容不会误关，这样我能安心在里面操作。
9. 作为管理员，我想输入类操作确认后立刻关闭，这样我能马上回到会话，不用等服务端回话。
10. 作为管理员，我想输入类操作失败时看到一条错误，这样我知道值没写上、需要重来。
11. 作为管理员，我想删好友时看到一句明确的确认描述，带上那位好友的名字，这样我不会删错人。
12. 作为管理员，我想踢人时看到带成员名字的确认描述，理由同上。
13. 作为管理员，我想确认破坏性操作后看到「处理中...」并且两个按钮都点不动，这样我知道它在跑、也不会重复提交。
14. 作为管理员，我想破坏性操作成功后对话框自动关闭，这样我不用再点一次。
15. 作为管理员，我想破坏性操作失败时对话框留在原地、按钮恢复可用，这样我能直接重试而不用重新走一遍右键菜单。
16. 作为管理员，我想上一次失败之后重新打开对话框时按钮是可用的，这样它不会卡在「处理中...」。
17. 作为管理员，我想在打开对话框后焦点落在对话框里，这样我能直接用键盘。
18. 作为管理员，我想关闭对话框后焦点回到我原来的位置，这样我不会丢失上下文。

### 插件维护者

19. 作为维护者，我想让「确认对话框失败后保持打开」有断言，这样这条最容易被顺手改坏的行为坏了我立刻知道。
20. 作为维护者，我想让「处理中禁用两个按钮」与「不双提交」各有断言，这样破坏性动作不会因为一次连点被发两遍。

23. 作为维护者，我想让「对话框开着」与「提交回调在场」是同一个事实，这样不可能出现开着但没回调的中间态。

27. 作为维护者，我想让共用 Dialog 的遮罩与内容"同时存在"有一条运行时守卫，这样生产兼容规则要防的那种退化不只靠源码文本兜。
28. 作为维护者，我想让锁实现语句的源码断言被行为断言接管后就删掉，这样测试不会两次描述同一件事。
29. 作为维护者，我想让锁文案契约的源码断言原文保留，这样这轮改动不会顺手削掉别的守卫。
30. 作为维护者，我想让两套完成协议的存在理由被写进 ADR，这样下一次架构复查不会再提议合并它们。
31. 作为维护者，我想让编排的形态与其他 store 一致，这样读过一个就读得懂这一个。
32. 作为维护者，我想让六个调用点的 diff 接近于零，这样审查时容易看出这次搬迁没有夹带行为改动。

### 接手实现的 agent

33. 作为接手的 agent，我想知道这轮为什么不做统一 Escape 栈，这样我不会去动被生产兼容规则保护的挂载路径。
34. 作为接手的 agent，我想知道哪些浮层不在本轮范围内，这样我不会把所有二级面状态都搬一遍。
35. 作为接手的 agent，我想知道挂载测试的替身需要 mock 到什么程度，这样我不会卡在模块作用域的调用上。
36. 作为接手的 agent，我想知道哪些源码断言该删、每条由谁接管，这样我不会删掉没有替代的守卫。
37. 作为接手的 agent，我想知道本轮唯一允许的行为改动是哪一处，这样其余部分我按逐字等价搬迁处理。

## Implementation Decisions

### 范围为什么与复查报告不同

报告把候选 ④ 定成「合并两份同构的对话框状态机 + 收成一个 Escape 栈」。核对后两条前提都不成立，范围据此重划：

- **状态袋同构，状态机不同构。** 两个对话框的完成协议实质不同（一个发射后不管、一个 await 且失败保持打开）。合并只有两种结局：保留两套协议（那"合并"只剩表面），或统一（真的行为改动，与报告承诺的"界面外观不变"矛盾）。决定保留两套，理由与替代方案见 ADR 0007。
- **报告想象的那个"唯一 Escape 栈"不存在。** 一级工作区那条 Escape 分支根本不管对话框，它只管会话内查找、转发目标、多选模式与回复目标；三个基于共用 Dialog 的浮层由 Dialog 内容层自己的 Escape 处理器负责，而那个处理器带 `.stop`——分层正是靠它生效。要收成一个栈得先拆掉 `.stop`，而那条挂载路径被项目的生产兼容规则点名保护。

成立的是「16 个平铺状态名」这条，本轮针对它。

### 编排的形态与命名

编排落成 `stores/` 下的 composable，与既有 store 同款（注入 ref 与函数，返回状态与动作），不做成组件——判据同 ADR 0004：行为长在 DOM 上才做组件，而这段编排一行 DOM 都不碰。

命名避开 `interaction` 这个词：仓库里它已经被交互状态与交互样式占用，再叠一层含义只会让搜索变难。也避开泛化的「所有对话框」式命名——转发目标框与资料卡不在这个模块里，名字不能骗人。选定的名字与既有的输入对话框组件对齐，读作「用来完成一次动作的对话框」。

### spec 对象与提交回调

这是本轮的核心形状。每一类对话框由一个可空的 spec 引用表示，**提交回调是 spec 的一个字段**，不是旁边的可变量。于是：

- 「对话框开着」与「提交回调在场」是同一个事实，不可能出现开着但没回调的中间态；那句 `if (!submit)` 的补丁守卫连存在的理由都没有。
- 独立的开关布尔不再需要。模板侧的双向绑定接一个带 setter 的计算值，置为关闭就清掉 spec。
- 取消、Escape、点遮罩三条关闭路径自动清掉回调，不需要各自补一行。

两类 spec 是两份独立类型，不做带判别字段的联合类型：字段本来就不同（输入型有占位文案与初始值，确认型没有；确认型的确认按钮文案三个调用点都显式传，输入型三个调用点一个都没传、全走默认），协议也不同。做成联合只会让每个消费点先写一遍判别。

### 对外接口

注入只有一项：共享的错误横幅引用。错误文案读取是纯函数，直接 import 不注入。

对外 8 个名字：两份 spec 引用、两个带 setter 的开关计算值（供模板双向绑定）、两个打开函数、两个提交函数。比现在的 16 个少一半。

调用点侧的函数名保持贴近现状，六个调用点只改其中一个的名字，这样这次搬迁在调用点几乎是零 diff——审查时容易看出没有夹带行为改动。

### 错误落点

错误横幅是**共享的**：消息列表在渲染它，一级工作区里有十个以上写入点（发送失败、加载联系人、加载资料、通用交互包装、两个对话框、四处硬编码的「当前不是群聊」）。所以 module 不能自己拥有它，必须注入同一个引用。`'操作失败'` 这句 fallback 收进 module 写一次。

### 两套协议留在组件里

module 只统一 spec 与回调生命周期。「确认后立即关闭」与「处理期间保持打开、失败留在原地」这两套协议留在各自的对话框组件里，本轮不动它们的实现，只给它们立断言。

### 唯一的行为修正

关闭时清掉提交回调。按上面的 spec 形状是自动成立的，不需要额外代码。这处修正不可见——现在的泄漏被「下一次打开覆写」掩掉了。除此之外按逐字等价搬迁处理。

### 不进本轮的四个浮层

资料卡、表情选择、图片预览、合并转发不收进来。它们各自只有一两个状态，没有提交回调，也没有完成协议；收进来只会把本轮变成「把所有二级面状态搬个家」，那是没有杠杆的搬迁——删掉它也不会有复杂度聚集。

资料卡与表情选择缺 Escape 关闭这件事另立了票（`.scratch/portal-page-escape/`），与本轮无阻塞关系。

### 新增领域术语

`CONTEXT.md` 新开一节 `对话框`，两条：**输入对话框**（征询一个值，确认后立即关闭，不等动作完成）与**确认对话框**（征询一次确认，处理期间保持打开，动作失败时留在原地供重试）。两者协议不同是本轮的核心事实，散文里必须能一句话分开说；原先只有「实体二级面 / 雾化二级面」这种视觉层面的词。

## Testing Decisions

### 什么算好测试

只测外部行为。对两个对话框组件来说，外部行为是「给定 props 与真实事件，渲染结果与对外事件应当是什么」；对编排来说，是「给定注入的错误引用与一串动作，spec 状态与对回调的调用应当是什么」。断言源码文本不算测行为——它锁的是实现语句，等价改写会误报，改坏行为反而可能照过。

### 两个接缝，都已存在

1. **两个对话框组件的挂载面**。与输入区、查找页那几个测试文件同款：`@vue/test-utils` 加无头 DOM，按文件开环境。两个组件都是纯 props/emits，不需要任何改造。
2. **编排的 options 对象**。直接实例化、注入假的错误引用、调动作、读 spec 状态，跑在默认 node 环境。

不新造接缝。协议的**表现**（按钮禁用、文案变化、失败后还在）只有挂载看得到；回调的**生命周期**在编排上测最直接。

### 挂载要测的行为（14 条）

输入对话框：打开时遮罩与内容同时存在、关闭时两者都不在；打开时输入框预填初始值；重开刷新成最新初始值；打开期间外部改初始值会同步进输入框；回车提交并带当前输入值；点确认提交；点取消只发出关闭、不发出确认；Escape 关闭；点遮罩关闭、点内容不关；确认按钮文案默认「保存」且可覆盖。

确认对话框：处理中两个按钮都禁用且确认按钮文案变「处理中...」；成功后关闭；失败后**保持打开**、按钮恢复可用、不产生未处理的 promise rejection；处理中再点确认不会二次提交；每次打开把提交态重置。

### 实例化要测的行为（11 条）

打开后 spec 在场；提交把值交给该 spec 的回调；提交后 spec 清空；回调抛错时错误落进注入的引用且 fallback 为「操作失败」；输入型提交后立即关闭、不等回调完成；确认型成功才 resolve 才清 spec；确认型失败时 reject、错误落进引用、**spec 仍在场可重试**；取消清空 spec 与回调；取消后再提交调不到上一次的回调；两类对话框先后打开互不干扰；接口宽度用键集合全等钉住。

### 已知的挂载准备

Dialog 内容层在模块作用域链到控制台客户端的颜色模式钩子（经 WebQQ 设置模块），所以替身必须连它一起 mock，不只是代理地址函数——查找页那张票踩过同一条。无头 DOM 没有 Popover API，但浮层提升工具本来就守了这个判断并静默返回，不妨碍挂载；测不到的只有「被提升到 Top Layer」，那由保留的样式契约断言覆盖。

### 保留与删除

删 1 条：锁删好友确认描述模板字面量的那条源码断言。接管者是行为断言「请求删除好友时，确认对话框的描述为『确定删除好友「Alice」？』」。

原文保留：那条防止啰嗦文案回归的 `not.toContain`（它是文案契约，行为断言只能证明现在是短的，证不了长的那句没在文件别处冒出来）；样式契约里锁 Dialog 挂载路径与层级的几条。

### Prior art

编排测试的范本是通知菜单那条断言（注入假函数、事件序列断言）。挂载式断言的范本是输入区那四个测试文件与它们的脚手架。会话内查找那轮刚立的查找页挂载断言与本轮形态最接近，可以直接照抄脚手架写法。

## Out of Scope

- 改两个对话框的界面、文案或交互。除「关闭时清掉提交回调」这处不可见修正外，按逐字等价搬迁处理。
- 合并两套完成协议，或把它们统一成带开关的一套。ADR 0007 已否。
- 收成一个统一的 Escape 栈，或改动共用 Dialog 的挂载路径与它那个带 `.stop` 的 Escape 处理器。前提不成立，且该路径被生产兼容规则保护。
- 把资料卡、表情选择、图片预览、合并转发的状态搬进本模块。
- 给资料卡与表情选择补 Escape 关闭。已另立票。
- 共用 Dialog 组件自身的任何改动。本轮只读它、给它加一条运行时守卫，不改它——因此不触发生产兼容规则要求的完整生产构建加真实浏览器验证流程。
- 那四处硬编码的「当前不是群聊」文案。它们与对话框无关，属于通用交互包装那条路径。

## Further Notes

### 验收清单

两张票各自的验收写在票里。共同要求：全量测试通过；删掉的源码断言能指名接管者；逐条失效实测（故意改坏 → 对应断言变红 → 改回）。

### 真实浏览器

本轮不需要。这条路径上没有输入法、没有剪贴板、没有需要真实布局的几何计算。唯一涉及真实浏览器的是共用 Dialog 的挂载路径，而本轮不改它——反而给它加了一条运行时守卫，让那条生产兼容规则第一次有自动化兜底（原先只有源码文本守着，那种守法抓不到挂载路径退化）。

### 为什么先立断言再搬迁

两张票互不阻塞，但建议按 01 → 02 的顺序做：01 生产代码零改动，是零风险的安全网；02 搬迁时靠它兜住。先立断言再动代码，在这里有实际价值而不只是流程洁癖——两个对话框的协议差异细微（一个先关后跑、一个跑完再关），搬迁时最容易犯的错就是把其中一个的顺序写成另一个的。

### 那两个模块级可变量留下的痕迹

编排里那句「操作已失效」的拒绝分支，是这套设计撞过「回调不见了」的直接证据。本轮之后它不该继续存在——如果实现时发现还需要它，说明 spec 对象的形状没有真正落地，值得回头看一眼而不是把守卫补回去。
