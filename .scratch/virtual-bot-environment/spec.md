# 开发者模拟环境改由虚拟 OneBot 机器人提供

Status: ready-for-agent

来源：会话中对两种方案的比较，决策已收敛。约束见 ADR 0001（源码分层）与 ADR 0003（配置规格边界）。配套的 sandbox 侧 action 缺口另立于该仓库的 `.scratch/onebot-capability-closure/`。

---

## Problem Statement

插件维护者开启「启用 WebQQ 开发者模拟环境」后，看到的是一份写死在代码里的场景：一台机器人、一个群、几条预设消息。改任何一处都要改代码再构建。建不了群、加不了好友、造不出一条加群申请，也没法让另一个人发消息进来。

更要紧的是这个模拟环境验证不了它最该验证的东西。开关一开，整个 WebQQ service 被换成内存实现，真实路径上那 894 行 OneBot 适配代码、以及监听 Koishi 事件的实时消息链路，一行都不执行。所以模拟环境里一切正常，不代表接上真机正常。

这个盲区已经藏过两个真实缺陷：表情回应的「谁贴了」在 NapCat 上必然失败（参数拼写与上游不符），语音转文字在 NapCat 上调的是一个不存在的 action 名。两条都发生在 action 调用层，而模拟环境从不执行那一层。

维护成本也是双份：内存实现 750 行、写死场景 622 行，必须手工跟随真实适配层演进，两者靠一个联合类型约束同构，漏改不会报错，只会在某天表现成「模拟环境好用、真机不对」。

## Solution

开关的含义改成「把**虚拟 OneBot 机器人**纳入 WebQQ」。

装一个提供虚拟 OneBot 机器人的插件（当前是 `koishi-plugin-chatluna-sandbox`），开开关，**一级工作区**里就出现那台机器人；会话、消息、群成员、通知、群公告全部来自它的场景，读写走的是和真机完全相同的 OneBot action。

对维护者来说，场景在那个插件自己的界面里随手改：建群、加好友、造一条加群申请、以别人的身份发消息进来，WebQQ 收到的是真实 Koishi 事件。一次改动同时验证适配层和实时链路。内存实现与写死场景一起删掉，双份维护消失。

onebot-webqq 不引用那个插件的任何代码，`package.json` 不加依赖。开关认的是一个通用形状：platform 为 `onebot`、对 UI 隐藏、具备 action 通道。将来任何插件提供这种机器人都能当后端。

开关开启期间真实 OneBot 机器人不出现在 WebQQ 里。这一条的分量不在整洁：WebQQ 的撤回、踢人、禁言、改群名都真发 action，两边混列就可能在「模拟环境」里撤掉真实群的消息。

## User Stories

### 插件维护者

1. As a 插件维护者, I want 开启开发者模拟环境后 WebQQ 里出现虚拟 OneBot 机器人, so that 我不必接一台真实 QQ 就能验证观察窗
2. As a 插件维护者, I want 模拟环境下的读取走真实 OneBot action, so that 适配层的缺陷能在模拟环境里被发现而不是等到接真机
3. As a 插件维护者, I want 模拟环境下的实时消息走真实 Koishi 事件, so that 实时链路、撤回与通知的处理都能被验证
4. As a 插件维护者, I want 在提供方插件的界面里改场景就能改变 WebQQ 看到的内容, so that 我调整验证条件不需要改代码再构建
5. As a 插件维护者, I want 以别人的身份发消息进来后观察窗立刻刷出, so that 我能验证入站消息的渲染与滚动
6. As a 插件维护者, I want 在 WebQQ 里发出的消息能在提供方插件那边看到, so that 我能确认发送路径真的落到了场景里
7. As a 插件维护者, I want 模拟环境下发送失败时得到明确错误, so that 我能区分「插件没发出去」和「场景拒绝了这次动作」
8. As a 插件维护者, I want 开关开启时真实机器人不出现, so that 我不会在模拟环境里误撤真实群的消息
9. As a 插件维护者, I want 没有任何虚拟机器人时看到一句说清原因的提示, so that 我知道要去装提供方插件而不是怀疑观察窗坏了
10. As a 插件维护者, I want 配置项名称保持不变, so that 我现有的配置文件升级后继续可用
11. As a 插件维护者, I want 开关关闭后一切回到只看真实机器人, so that 我不必为了回到正常模式重启或改别的配置
12. As a 插件维护者, I want 虚拟机器人的头像、昵称与在线状态照常显示在**主胶囊**上, so that 我在胶囊上就能看出当前对着哪台机器人
13. As a 插件维护者, I want **胶囊对话状态**在模拟环境下照常更新, so that 胶囊的行为不需要按模式分别验收
14. As a 插件维护者, I want 模拟环境下的好感度与关系徽标照常按真实 ChatLuna 数据渲染, so that 我不必记住哪些界面元素在模拟环境里是假的
15. As a 插件维护者, I want 虚拟机器人在 ChatLuna 数据库里查不到记录时徽标为空, so that 我看到的是真实的「没有数据」而不是编出来的数值
16. As a 插件维护者, I want 图片、语音、视频、合并转发在模拟环境下走与真机相同的解析路径, so that 媒体渲染的缺陷不会被模拟环境掩盖
17. As a 插件维护者, I want 撤回、贴表情、引用回复在模拟环境下用同一套消息 ID, so that 我不必关心两种模式的 ID 形态差异
18. As a 插件维护者, I want 群公告、群成员、加群申请在模拟环境下从场景真实读出, so that 群资料栏与通知菜单都能被验证
19. As a 插件维护者, I want 提供方插件缺某个 action 时观察窗只少那一块而不是整体失败, so that 我能在能力不全的场景下继续验证其余部分
20. As a 插件维护者, I want 内存实现与写死场景被删掉, so that 我改适配层时不必再同步维护第二份
21. As a 插件维护者, I want 模拟环境不再有任何只在它里面生效的分支, so that 我在模拟环境里看到的行为可以直接推断到真机
22. As a 插件维护者, I want 提供方插件换成别的实现也能工作, so that 我不被绑定在某一个特定插件上
23. As a 插件维护者, I want onebot-webqq 不增加任何 npm 依赖, so that 插件体积与安装时间不受影响
24. As a 插件维护者, I want 模拟环境与真实环境共用同一份适配层测试, so that 一条断言同时守住两种模式

### Koishi 管理员

25. As a Koishi 管理员, I want 不开这个开关时插件行为完全不变, so that 我不必因为一次开发者功能的改造重新验收
26. As a Koishi 管理员, I want 开关仍然在「开发者选项」分组里, so that 面板布局与我熟悉的一致
27. As a Koishi 管理员, I want 开关的说明文案说清它需要一个提供方插件, so that 我不会开了之后不知道为什么没反应
28. As a Koishi 管理员, I want 没装提供方插件时开关不会让控制台报错, so that 误开一个开发者开关不会影响我正常使用
29. As a Koishi 管理员, I want 真实机器人的可用性判定、探测与在线指示不受本次改造影响, so that 我依赖的胶囊指示灯行为不变
30. As a Koishi 管理员, I want 配置面板的分组、字段顺序与控件类型一处不变, so that 我的操作习惯不被打断
31. As a Koishi 管理员, I want 浏览器产物不因本次改造变大, so that 控制台加载速度不受影响
32. As a Koishi 管理员, I want 升级后不需要迁移任何数据, so that 升级是一次纯粹的替换

## Implementation Decisions

**开关语义与配置项。** 保留配置键 `webQQMockEnvironment` 不改名——改名会让现有配置静默失效，收益只有名字更贴切。只改**配置规格**里那一项的说明文案，把「启用 WebQQ 开发者模拟环境」的含义写成「把虚拟 OneBot 机器人纳入 WebQQ，需要另装提供方插件」。它不是**镜像配置项**，不下发前端，本次也不改变这一点。配置改动遵守 ADR 0003：规格 module 不引用 `koishi`，`Config` 保持手写 interface，双向键集断言照旧成立。

**机器人选择层承接过滤变化。** 「哪些机器人算可用」这件事按 ADR 0001 归 `src/onebot/`，本次改动落在那里而不是散进适配层。该层的 bot 枚举现在无条件排除 `hidden` 为真的机器人；改成由调用方传入「是否纳入虚拟机器人」这一个标志，两种取值分别对应今天的行为和模拟环境的行为。可用性判定、action 通道探测、在线状态推导都不改判据，只改候选集合。

**开关开启时只列虚拟机器人。** 不是「把虚拟的加进来」而是「换成虚拟的」：真实机器人在开关开启期间从候选集合里消失。理由是 WebQQ 的写动作真发 action，混列可能让人在模拟环境里操作真实群。

**开关开启时绕过 selfId 白名单。** 现有配置允许把 WebQQ 限定在指定 selfId 上；虚拟机器人的 selfId 由提供方插件决定，不可能出现在管理员手写的白名单里。开关开启时白名单不参与筛选，否则配了白名单的人永远看不到虚拟机器人。

**内存实现与写死场景整体删除。** `webqq/adapters/mock/` 两个文件一起删。删掉之后 `webqq/adapters/` 只剩 ADR 0001 点名的 `onebot/` 一个，比今天更贴合那份分层。

**WebQQ service 类型收敛成单一形状。** 今天它是「真实实现 ∪ 内存实现」的联合类型，靠这个联合约束两份实现同构。删掉内存实现后收敛为单一形状，「两份实现必须同构」这条约束连同它守护的问题一起消失。

**服务装配不再按开关分叉。** 运行时装配今天按开关三元选择两种 service，改成永远创建真实实现，开关只作为一个选项传进去。装配层因此回到 ADR 0001 描述的「很薄，只创建和传递共享依赖」。

**删掉唯一一条只在模拟环境生效的界面分支。** 消息列表的好感度徽标今天在模拟环境下被整体跳过，理由是内存场景自带确定性的关系数据、不能混入真实 ChatLuna 数据库。虚拟机器人没有这个问题：它在真实数据库里查不到记录时徽标就是空的，那是正确答案而不是缺陷。这条分支删除，模拟环境与真实环境走同一条渲染路径。

**额外模拟机器人数量在模拟环境下不再生效。** 那个配置项今天在两种模式下都会派生出假的机器人画像用来验证多机器人界面。模拟环境下不再需要——提供方插件里可以真的建多台机器人，走真实 action。真实环境的行为一字不变。

**缺提供方时给出可行动的提示。** 开关开启但一台虚拟机器人都没有时，不能落到现有那句「未找到可用的 OneBot 机器人」上——那会让人以为观察窗坏了。这种情形要有自己的文案，说清需要另装一个提供虚拟 OneBot 机器人的插件。开关关闭时的原有文案不变。

**领域词汇新增两条。** 根目录领域文档里补「虚拟 OneBot 机器人」（由其他插件注册进 Koishi、platform 为 `onebot`、对 UI 隐藏、action 通道由该插件在自有场景中实现的机器人）与「开发者模拟环境」（把虚拟 OneBot 机器人纳入 WebQQ 的运行模式，场景由提供方插件持有）。后者今天在代码与配置文案里已经在用，但领域文档里没有词条，含义正好在本次改变。

**写一条 ADR。** 记「模拟环境靠通用形状接后端，不引用提供方插件」这个决定：为什么不 `inject` 提供方的 service（发布节奏解耦、语义通用、不引入类型依赖），为什么不把虚拟机器人做成本插件自己的实现（那等于重造一个沙盒，且仍绕不开写死场景），以及「开关开启时只列虚拟机器人」的安全理由。ADR 0002 已经为两个插件共存做过 CSS 层面的隔离，本条与它不冲突。

## Testing Decisions

**好测试只断言外部行为。** 断言的是「WebQQ service 对外交出什么」与「哪些 action 真的被调用、参数是什么」，不断言内部函数怎么分派、候选集合怎么算。本次尤其要避免把「过滤逻辑写在哪个函数里」写进断言——那是这次要挪动的东西。

**零新增接缝，主接缝沿用 WebQQ service 的构造入口。** 全部新行为都能在这个接缝上断言：虚拟机器人就是一个带「对 UI 隐藏」标记的假 bot，走真实 action 就是在它的 action 通道上挂 spy 并断言真的被调用、参数正确。**这个接缝上已有先例**：现有断言里已经在用「把某台 bot 标成隐藏后可用列表变空」来覆盖今天的过滤行为，本次是把同一条断言按开关取值分成两种预期。

**另外三处各用一次现有接缝，不新开。** 插件装配层的现有测试做一次端到端确认，断言开关开启后控制台收到的机器人列表只含虚拟机器人；配置四端一致性由现有的配置规格守卫覆盖新的文案与语义；「内存实现真的删干净了」由现有那类源码守卫断言覆盖，包括不再有任何 module 引用被删目录、service 类型不再是联合类型。

**现有的模拟环境专项测试文件按覆盖意图处置，不整体保留。** 它的五条用例里，预设联系人与消息元素、视频消息、内存状态变更这三条覆盖的是被删掉的实现，随实现一起删；额外模拟机器人数量那条改为断言「模拟环境下不再派生假画像」；「与真实 ChatLuna 数据隔离」那条覆盖的正是本次要删掉的分支，改为反向断言「模拟环境下好感度徽标照常按真实数据渲染」。文件改名以反映新语义。

**不为提供方插件写集成测试。** 本仓库的测试不装那个插件、不引用它的类型。它是否真的提供了某个 action 是它自己的事；本仓库只断言「拿到这种形状的机器人时行为正确」。

## Out of Scope

- 提供方插件那侧缺的四个 action（群公告读取、群系统消息、好友备注写入、表情回应参与者），已另立于该仓库的 `.scratch/onebot-capability-closure/`。缺它们时本仓库的表现是群资料栏与通知菜单少几块数据，不影响本 spec 验收。
- 建模「实现只给 file id、迫使插件二次取回」的媒体行为，以及随之而来的图片与语音取回 action。已判定不做。
- 语音转文字。提供方插件没有转写模型，已判定不做。
- 两个插件的 WebQQ 界面合并或代码复用。同一份场景在两处显示是刻意的，正好互为对照。
- 真实环境下「额外模拟机器人数量」的行为，一字不变。
- 提供方插件的场景编辑界面、测试端点、持久化，全部属于那个仓库。
- 观察窗的任何视觉改动。本次不碰样式，**实体二级面**与**雾化二级面**的行为不变。

## Further Notes

**提供方插件开箱即用，不需要先手工建机器人。** 它的默认场景自带一台虚拟机器人（实现配置为 NapCat）、三个测试用户、一个测试群（机器人在群里是管理员）和一条群公告，运行时机器人注册默认开启。机器人的 selfId 是 QQ 号形式的数字字符串，本仓库现有的 ID 归一化直接吃得下，不需要特殊处理。

**双向链路都真实。** WebQQ 里发出的消息经 action 写入提供方的场景，在它的界面与调试记录里都能看到，返回的是数字消息 ID，撤回与贴表情拿它能对上。反向以别人身份发消息时，提供方派发的是真实 Koishi session 并按真实适配器的形状嫁接 OneBot 载荷，本仓库的实时消息链路照常收到——这条链路在今天的模拟环境里一行都不执行。

**发送失败是有语义的。** 提供方会先校验机器人能否看到目标会话再落媒体，所以机器人不在群里时发送会返回 action 错误而不是静默丢弃；媒体有大小上限与类型白名单，超限明确失败。这些都会经现有的错误文案路径显示。

**验收时值得实地跑一遍的两件事。** 一是在提供方界面里改场景后观察窗能跟上；二是提供方缺 action 时观察窗只少对应那一块。两者都不适合写成自动化断言（依赖另一个插件），但适合在验收时手动确认一次。
