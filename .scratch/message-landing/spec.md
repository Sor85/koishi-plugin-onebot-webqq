# 消息落地：顺序与实时消息行为交给断言

**Status:** ready-for-agent

**来源:** `/improve-codebase-architecture` 的候选 ⑥，经 `/grilling` 三轮定型。范围与报告原提议有实质差异，理由见下。相关决定：ADR 0009（顺序断言的形式，本轮新立）、ADR 0001（运行时装配层的定位与领域依赖方向）、ADR 0005（开发者模拟环境）。

## Problem Statement

一条消息进入插件后要依次做四件事：标记 Bot 活动、记**主胶囊**计数、落 WebQQ 实时消息、刷新空闲日程。这个次序是真实不变量，前两步的先后尤其要紧——收到真实消息本身已经证明 action 通道刚刚可用，所以要先记活动再让 WebQQ 读 Bot 状态；反过来的话，适配器仍上报 OFFLINE 时 WebQQ 会永久把这个 Bot 排除掉，管理员看到的是「观察窗里这个机器人的消息不出现」。顺序错在别处则表现为未读数不对。

这条不变量目前只有三对源码位置比较守着——断言某个字符串在源文件里的首次出现位置小于另一个。它证明的是「源码里这一行排在那一行前面」，不是「运行时先做了这件事」；而且取首次出现位置意味着它悄悄依赖那几个字符串不出现在任何更早的注释里，而同一个文件的注释里已经出现过其中一个方法名。改一句注释就可能让它量错对象且不报错。

更大的洞在下一层：**实时消息落地这条链路 423 行，一条行为断言都没有**。唯一"覆盖"它的方式是把它当源码文本读。里面有 thinking 与 token 用量的状态机（四个模块级可变量）、撤回落库、以及一处按容量淘汰最旧会话的缓存逻辑——最后这条是全链路唯一会**静默丢数据**的分支。

## Solution

两块，都不改管理员看到的行为。

第一块给实时消息落地立行为断言。它本来就是「注入九项依赖、返回七个动作」的形状，不需要改造就能直接实例化；缺的只是有人去测。thinking 挂载、用量记与取、撤回落库、缓存淘汰从此坏了会变红。

第二块把四步扇出从装配层收成一个 module，四个下游依赖全部注入。顺序由测试的假实现按调用与完成两类事件记录，断言完整序列——于是改错次序或删掉某个 `await` 都会立刻变红。装配层回到纯接线，符合 ADR 0001 对它的定位。生产代码不为此返回任何步骤清单（ADR 0009）。

## User Stories

### Koishi 管理员

1. 作为管理员，我想每个在线机器人的消息都出现在观察窗里，这样我不会以为某个 Bot 掉线了。
2. 作为管理员，我想主胶囊上的收发计数与实际消息一致，这样它是可信的。
3. 作为管理员，我想会话未读数不多不少，这样徽标能当提醒用。
4. 作为管理员，我想隐藏机器人的消息既不进主胶囊也不进 WebQQ 未读，这样两处状态不会被污染。
5. 作为管理员，我想开启开发者模拟环境后，只有虚拟机器人的消息进来，真实群的消息不混进去。
6. 作为管理员，我想角色思考过程挂在对应的那条外发消息下面，而不是挂错一条。
7. 作为管理员，我想 token 用量只显示一次，不会重复贴到后面几条消息上。
8. 作为管理员，我想被撤回的消息在开启标记模式后仍能在历史里看到，这样我知道发生过什么。
9. 作为管理员，我想会话很多时旧会话的实时缓存被淘汰不影响当前会话，这样内存不会无限涨、当前对话也不丢。
10. 作为管理员，我想这轮改动之后界面与行为一点变化都没有，这样它对我是完全透明的。

### 插件维护者

11. 作为维护者，我想**消息落地**的四步次序能在运行时被证明，这样它不再依赖源码里的行序。
12. 作为维护者，我想删掉某一步前面的 `await` 时断言变红，这样「上一步做完才做下一步」这半条不变量也有守卫。
13. 作为维护者，我想生产代码不为了让测试观察而多攒一份步骤清单，这样接口宽度反映真实需求。
14. 作为维护者，我想那三对源码位置比较断言被删掉，这样测试不会用「某行字在前面」冒充「运行时先做了这件事」。
15. 作为维护者，我想可见性门禁落在落地流程内部并可断言，这样「隐藏机器人要在共享扇出边界阻断」这条不变量有唯一的检查点。
16. 作为维护者，我想装配层回到只创建和传递依赖，这样它符合 ADR 0001 对它的定位。
17. 作为维护者，我想实时消息落地的用量状态机有断言（记、取、不重复取三条独立），这样那四个模块级可变量的失效形态都被钉住。
18. 作为维护者，我想缓存容量淘汰有断言，这样全链路唯一会静默丢数据的分支不再没人看着。
19. 作为维护者，我想撤回落库有断言，这样标记撤回模式坏掉时不用等用户发现历史里少了东西。
20. 作为维护者，我想 thinking 在外发消息还没到时先存起来、到了再合并这条时序有断言，这样它不会退化成「有时挂上有时不挂」。
21. 作为维护者，我想好感度徽标在配置关闭时不附加这条有断言，这样配置开关是可信的。
22. 作为维护者，我想 Koishi 上下文替身住在共享测试脚手架里，这样它不再是第四份复制。
23. 作为维护者，我想这条主链路的改动经过真机验证，这样我不必只靠断言就敢发版。
24. 作为维护者，我想真机验证不需要连真实 QQ 群，这样它可以反复做。

### 接手实现的 agent

25. 作为接手的 agent，我想知道报告里哪一条论据是错的，这样我不会去做一个不存在的收益。
26. 作为接手的 agent，我想知道顺序断言为什么不能只记调用次序，这样我不会写出一条抓不到回归的断言。

28. 作为接手的 agent，我想知道实时消息落地本轮不拆，这样我不会在没有安全网的情况下重构主链路。
29. 作为接手的 agent，我想知道上下文替身已经存在、只是位置不对，这样我不会重写一份。
30. 作为接手的 agent，我想知道本轮没有任何允许的行为改动，这样我按等价搬迁处理。

## Implementation Decisions

### 范围为什么与复查报告不同

报告把候选 ⑥ 定成「让扇出顺序成为可断言的返回值 + 把合并入口从 2 收成 1」。核对后有一条不成立，另有一处比报告说的严重，范围据此重划。

- **「实时消息合并有两个入口、改规则要改两处」不成立。** 合并是一个纯函数，只有一份实现，而且已经有直接比对返回值的真断言。它被五处调用（控制台三处、实时运行时两处）只是正常复用——合并**规则**本来就只有一处。这个收益不存在，从范围里去掉。
- **源码位置断言比报告说的更脆。** 见 Problem Statement：取首次出现位置，因此依赖那几个字符串不出现在更早的注释里。
- **真正的洞是实时消息落地零行为覆盖。** 这比顺序值钱得多，本轮的重心放在它上面。

### 扇出 module 的形态与位置

收成一个可直接实例化的 module，四个下游依赖全部注入，落在运行时装配层旁边而不是 WebQQ 领域内部。

放进 WebQQ 的消息流目录会让 WebQQ 领域去指挥主胶囊，撞上 ADR 0001 的依赖方向。而现状（写在装配层的事件监听器里）本身就是 ADR 0001 说的「装配层不写业务流程」被违反的样子；抽出来之后装配层回到纯接线，正好落回它该有的形状。

这四步的次序是**跨领域**编排，不属于任何单一领域——这是它需要一个中立位置的全部理由。

### 门禁与诊断日志的分工

可见性门禁进 module：它是这条流程的第一条不变量（隐藏机器人的事件要在共享扇出边界阻断，纳入虚拟机器人时判据反转），留在外面就不在接缝上、测不到。

诊断日志的**载荷构造**不进：它要遍历上下文里的全部 bot 并做序列化，还要读服务侧的诊断数据，整块搬进去会让 module 的注入面凭空宽三项。折中是 module 拥有日志的**位置**（门禁 → 日志 → 四步），通过一个可选注入的回调调用它，不拥有日志内容。

### 顺序断言的形式

假实现同时记录**调用**与**完成**两类事件，断言完整序列。生产代码不返回步骤清单。判据与被否掉的替代方案见 ADR 0009——要点是只记调用抓不到删 `await`，而那正是最可能出的错。

### 实时消息落地本轮不拆

它已经是「注入九项依赖、返回七个动作」的深模块形状，接口不宽。423 行的问题是**没测**，不是没拆。

本轮只立断言。拆不拆等断言在手之后再判断——反过来先拆是没有安全网的重构，而这是每条消息都要过的主链路。尤其不要按职责预先拆成三四个 module：现在还看不出哪条缝是真的，而它内部由两个子运行时（通知与表情回应）组合而成这件事说明真缝可能在别处。

### Koishi 上下文替身提取到共享脚手架

两张票都需要一个上下文替身。现成的那份住在最大的那个测试文件内部，提供事件注册、可选控制台（带监听器与入口收集器）、可选数据库与模型扩展、bot 列表、日志器——实时消息落地对上下文的全部用法它都撑得住（三处 ChatLuna 事件注册、走可选链的控制台广播、撤回缓存与好感度徽标要的数据库）。

把它提到共享测试脚手架目录，两张票共用，原文件改成 import。这是**有意与候选 ⑨ 重叠**：提取脚手架本身就是那个候选的一部分，本轮先把它做掉。不做的话只能在「再写第四份复制」和「让测试文件互相 import」之间选，两个都更差——后者跑单个文件时会拖起两千行的模块图，而那个文件顶层有十几个读文件操作。

提取是纯移动，不改替身的能力。

### 没有允许的行为改动

本轮是纯等价搬迁加断言，一处可见或不可见的行为改动都没有。与候选 ⑧ 相同、与 ③④ 不同（那两轮各带不可见修正）。

### 新增领域术语

领域词汇表新开一节 `消息`，一条：**消息落地**——一条消息进入插件后被各领域依次记录的过程，各步之间的先后次序是这个过程的一部分。定义里点明次序，因为本轮的核心不变量就是它。

## Testing Decisions

### 什么算好测试

只测外部行为。对扇出 module 来说，外部行为是「给定一个会话与一组注入的下游，实际发生的事件序列应当是什么」；对实时消息落地来说，是「给定注入的上下文与一串动作，广播出去的载荷、缓存里的内容、附加到消息上的字段应当是什么」。

断言源码文本不算测行为。那三对源码位置比较是本轮要消灭的反例：它们证明得了源码的行序，证明不了执行序，而后者才是这条不变量的全部内容。

### 两个接缝，都不新造

1. **扇出 module 的 options 对象**。四个下游依赖注入，假实现记录事件。这个 module 是新建的，但接缝落在最高点——就是那条共享扇出边界本身。
2. **实时消息落地的 options 对象**。九项注入已经存在，本轮只是第一次有测试用它。

上下文替身是这两个接缝共同的支撑设施，不是第三个接缝。

### 实时消息落地要测的行为（10 条）

会话选择门禁（非选中 Bot 的会话不记录）；实时消息按会话键进缓存；缓存容量超限时最旧的会话被淘汰；用量事件记下后下一条外发消息带上它；用量取用后不重复附加到第二条消息；用量不满足展示条件时不附加；思考过程挂到最后一条外发消息；外发消息还没到时思考过程先存起来、到了再合并；撤回广播对应载荷且标记撤回模式下另存一份显示缓存；好感度徽标在配置关闭时不附加。

用量那三条不合并——记、取、不重复取是三个独立失效点，那四个模块级可变量的状态机就靠它们钉住。缓存淘汰那条不能砍，它是全链路唯一会静默丢数据的分支。

### 扇出要测的行为（7 条）

完整事件序列（门禁 → 诊断日志 → 步一 → 步二 → 步三开始 → 步三完成 → 步四开始 → 步四完成），后两步用受测试控制的 deferred 造；隐藏 Bot 的会话被门禁挡掉且四步一个都不执行；纳入虚拟机器人时判据反转；诊断回调未提供时四步照常执行；装配层回到纯接线且那三对源码位置断言删除；**失效实测明确包含「删掉某一步前面的 `await`」必须变红**；真机验证。

倒数第二条要写成显式的失效实测项而不是普通断言。它是这套断言形式的验收：如果删 `await` 之后测试仍然全绿，说明假实现只记了调用没记完成，ADR 0009 的决定没有真正落地。

### 真机验证

走**开发者模拟环境**的**虚拟 OneBot 机器人**，不连真实 QQ 群。那条路径本来就走真实 OneBot action 与真实 Koishi 事件，所以这条链路能端到端跑通——正是为这种场景准备的。

要覆盖的是断言到不了的那一段：Koishi 事件真实派发之后，四步是否按序发生、观察窗是否收到实时消息、主胶囊计数与未读数是否正确。改的是每条消息都要过的路径，不能只靠单元断言发版。

### 保留与删除

删：那三对源码位置比较断言。接管者是扇出的完整事件序列断言。

保留未动：合并规则那几条直接比对返回值的断言（它们本来就在真接缝上）；装配层其余那些锁 import 来源与事件名的源码断言（它们锁的是接线结构，不是业务流程）。

### Prior art

直接实例化加注入假实现的断言，仓库里已有多处先例：通知菜单、会话内查找、以及本系列前几轮的成果。上下文替身与 `createPluginRuntime` 的真实实例化在最大的那个测试文件里已经用了三处，本轮沿用同一套。

## Out of Scope

- 让扇出 module 返回步骤清单或任何供测试观察用的返回值。ADR 0009 已否。
- 把实时消息落地按职责拆成多个 module。本轮只立断言，拆分等断言在手之后再判断。
- 收敛合并函数的调用点。合并规则本来只有一处，这个收益不存在。
- ChatLuna 的会话结束事件那条路径。它是另一个事件入口，且依赖外部插件的载荷形状，混进来会让替身面突然变大。
- 通知与表情回应两个子运行时的内部行为。本轮只测组合它们的那一层，它们各自已有部分覆盖。
- 改动消息落地的次序本身，或四步各自的实现。
- 把上下文替身的能力扩充。本轮只搬位置。
- 候选 ⑨ 的其余部分（另外两处重复的脚手架）。本轮只提取一份并让两张票共用。

## Further Notes

### 为什么两张票、为什么这个顺序

两张票互不阻塞，建议先做实时消息落地那张。要说清它的安全网作用**比前几轮弱**：那张测的是实时消息落地自己的行为，扇出搬迁换的是它的调用方，所以它不能直接兜住搬迁时的失误。

真正的理由是分量。实时消息落地 423 行、七个对外动作、含用量状态机与缓存淘汰，它自己就是一张完整的票；跟扇出搬迁绑在一起会超出一个上下文窗口。而且它生产代码零改动（除上下文替身的移动），是零风险的一张，先落地能让第二张的基线更干净。

### 上下文替身的移动要单独核对

它被最大的那个测试文件的多处用到。提取之后要确认那个文件仍然全绿——这是纯移动，但它是本轮唯一会碰到既有测试文件结构的改动，值得在验收里单列一条。

### 与候选 ⑨ 的边界

本轮只提取上下文替身这一份，不碰候选 ⑨ 提到的另外两处重复。原因是只有这一份被本轮的两张票需要；顺手把三处都收掉会让本轮的验收范围超出「消息落地」这个主题，而那三处各自的消费方不同，值得单独判断。

### 顺序不变量的来历

第一步与第二步的先后不是随手写的：收到真实消息本身已经证明 action 通道刚刚可用，所以先记活动再让 WebQQ 读 Bot 状态。这条约束在装配层有注释写明，实现时要把它连同注释一起搬进新 module——它是这条不变量存在的唯一解释，丢了之后下一个人会觉得四步顺序可以任意调整。
