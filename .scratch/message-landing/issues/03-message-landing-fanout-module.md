# 03 — 消息落地扇出收成 module

**What to build:** **消息落地**的四步次序从此能在运行时被证明。管理员看不到这条不变量，但它错了会直接表现成故障：前两步颠倒会让适配器仍上报 OFFLINE 时 WebQQ 永久排除该 Bot——观察窗里那个机器人的消息不出现；错在别处则表现为未读数不对。

现在守着它的是三对源码位置比较（断言某个字符串在源文件里的首次出现位置小于另一个）。这种断言证明的是「源码里这一行排在那一行前面」而不是「运行时先做了这件事」；而且取首次出现位置意味着它悄悄依赖那几个字符串不出现在任何更早的注释里，而同一个文件的注释里已经出现过其中一个方法名——改一句注释就可能让它量错对象且不报错。

本 ticket 把四步扇出从装配层收成一个 module，四个下游依赖全部注入，顺序由测试的假实现按事件序列断言。装配层回到纯接线，符合 ADR 0001 对它的定位。生产代码不为此返回任何步骤清单（ADR 0009）。

**Blocked by:** 无 — 可以立即开工。本票不需要 Koishi 上下文替身：四个下游全是假实现，会话是普通对象，所以与 01、02 完全并行。

**Status:** ready-for-agent

**参考:** `.scratch/message-landing/spec.md`；顺序断言的形式与被否掉的替代方案见 ADR 0009；装配层定位与领域依赖方向见 ADR 0001；真机验证走的环境见 ADR 0005。

- [ ] 四步扇出成为可直接实例化的 module，四个下游依赖全部注入；落在中立位置而不是 WebQQ 领域内部（跨领域编排不能让 WebQQ 去指挥主胶囊）
- [ ] 可见性门禁进 module；诊断日志的**载荷构造**留在外面，module 只通过可选注入的回调拥有它的**位置**（门禁 → 日志 → 四步）
- [ ] 装配层回到纯接线，不再持有业务流程
- [ ] 「先记活动再让 WebQQ 读 Bot 状态」那条注释连同代码一起搬进新 module —— 它是这条不变量存在的唯一解释
- [ ] 断言完整事件序列：门禁 → 诊断日志 → 步一 → 步二 → 步三开始 → 步三完成 → 步四开始 → 步四完成；后两步用受测试控制的 deferred 造
- [ ] 隐藏 Bot 的会话被门禁挡掉，四步一个都不执行
- [ ] 纳入虚拟机器人时判据反转：只有虚拟机器人的事件能进
- [ ] 诊断回调未提供时四步照常执行
- [ ] 生产代码不返回步骤清单，也不以其他形式对外暴露「我依次做了什么」
- [ ] 那三对源码位置比较断言已删除；装配层其余锁 import 来源与事件名的源码断言未动
- [ ] **失效实测必须包含「删掉某一步前面的 `await`」并且对应断言变红。** 若删掉后仍全绿，说明假实现只记了调用没记完成，ADR 0009 的决定没有真正落地，断言形式要改
- [ ] 其余逐条失效实测：调换任意两步次序、去掉门禁时对应断言失败
- [ ] 真机验证：走**开发者模拟环境**的**虚拟 OneBot 机器人**，不连真实 QQ 群；确认四步按序发生、观察窗收到实时消息、主胶囊计数与未读数正确
- [ ] 验证结束后按项目约定收尾（关闭本次开启的浏览器会话与自动化进程，清理工具生成的临时目录）
- [ ] 本轮没有任何行为改动，可见与不可见都没有
