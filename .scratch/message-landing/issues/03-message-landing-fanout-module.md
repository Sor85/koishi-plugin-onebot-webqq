# 03 — 消息落地扇出收成 module

**What to build:** **消息落地**的四步次序从此能在运行时被证明。管理员看不到这条不变量，但它错了会直接表现成故障：前两步颠倒会让适配器仍上报 OFFLINE 时 WebQQ 永久排除该 Bot——观察窗里那个机器人的消息不出现；错在别处则表现为未读数不对。

现在守着它的是三对源码位置比较（断言某个字符串在源文件里的首次出现位置小于另一个）。这种断言证明的是「源码里这一行排在那一行前面」而不是「运行时先做了这件事」；而且取首次出现位置意味着它悄悄依赖那几个字符串不出现在任何更早的注释里，而同一个文件的注释里已经出现过其中一个方法名——改一句注释就可能让它量错对象且不报错。

本 ticket 把四步扇出从装配层收成一个 module，四个下游依赖全部注入，顺序由测试的假实现按事件序列断言。装配层回到纯接线，符合 ADR 0001 对它的定位。生产代码不为此返回任何步骤清单（ADR 0009）。

**Blocked by:** 无 — 可以立即开工。本票不需要 Koishi 上下文替身：四个下游全是假实现，会话是普通对象，所以与 01、02 完全并行。

**Status:** resolved

**参考:** `.scratch/message-landing/spec.md`；顺序断言的形式与被否掉的替代方案见 ADR 0009；装配层定位与领域依赖方向见 ADR 0001；真机验证走的环境见 ADR 0005。

可以观察，因此那条不变量落在 `landMessage` 返回的 promise 上——测试用一个 `landed` 标记断言它在第四步
完成前不 settle。

扇出 module 落在 `src/message-landing.ts`（src 根，与 `runtime/` 平级）而不是 `src/runtime/` 内部：
ADR 0001 把 `runtime/` 定成「只创建和传递共享依赖，不写业务流程」的装配层，把落地流程放进那个目录
会让本轮想恢复的那句定义对该目录不再成立。理由写在 module 头部注释里。

真机验证（koishi-dev，`webQQMockEnvironment: true`，四个真实平台适配器在 koishi.yml 里全部带 `~` 停用，
数据库为本地 sqlite，不连真实 QQ 群）：改完服务端后完整重启一次，确认只有一个 worker 实例、5140 端口
由新进程持有、加载的是本次构建产物。从 chatluna-sandbox 场景以「测试用户1」向虚拟 OneBot 机器人
（selfId 20001）发一条私聊，四步的效果逐一出现：

- 步四 `refreshIdleScheduleActivity`：`conversation.activityText` 刷新为当前空闲日程

该环境未开 `debug`，因此诊断回调为 `undefined`，「诊断回调未提供时四步照常执行」这条也在生产路径上
