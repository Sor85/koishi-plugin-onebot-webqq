# ADR 0005：开发者模拟环境靠通用形状接后端，不引用提供方插件

## 状态

已接受。

## 背景

**开发者模拟环境**原本是一份写死在代码里的场景：开关一开，整个 WebQQ service 被换成内存实现，一台机器人、一个群、几条预设消息，改任何一处都要改代码再构建。

真正的问题不是场景贫瘠，而是它验证不了最该验证的东西。开关开启时，真实路径上的 OneBot 适配层与监听 Koishi 事件的实时消息链路一行都不执行，所以「模拟环境里一切正常」不能推断出「接上真机正常」。这个盲区已经藏过两个真实缺陷：表情回应的参与者查询在 NapCat 上必然失败（参数拼写与上游不符），语音转文字在 NapCat 上调的是一个不存在的 action 名。两条都长在 action 调用层，而模拟环境从不执行那一层。

维护成本也是双份：内存实现与写死场景必须手工跟随真实适配层演进，两者靠一个联合类型约束同构，漏改不报错，只会在某天表现成「模拟环境好用、真机不对」。

## 决策

开关的含义改成「把**虚拟 OneBot 机器人**纳入 WebQQ」。装一个提供虚拟 OneBot 机器人的插件，开开关，**一级工作区**里出现的就是那台机器人：会话、消息、群成员、通知全部经真实 OneBot action 从它的场景读出，实时消息经真实 Koishi 事件抵达。

- **靠通用形状认后端，不引用提供方插件。** 开关认的是「platform 为 `onebot`、对 UI 隐藏、具备 action 通道」这个形状，`package.json` 不加依赖，代码不 import 提供方的任何 module。
- **不 `inject` 提供方的 service。** 三个理由：两个插件的发布节奏就此解耦，任何插件提供这种形状的机器人都能当后端；语义保持通用，不需要为「谁是提供方」留一个专有名字；不引入跨插件的类型依赖，提供方改自己的 service 接口不会连带编译失败。
- **不在本插件里自造虚拟机器人。** 那等于在观察窗仓库里重造一个沙盒：既要实现 action 通道、又要实现场景编辑界面，而且仍绕不开「场景写死在代码里」这个原始问题——只是把写死的位置从 service 换到了假 bot 里。
- **开关开启期间只列虚拟机器人，真实机器人从候选集合里消失。** 不是「把虚拟的加进来」而是「换成虚拟的」。理由不是整洁：WebQQ 的撤回、踢人、禁言、改群名都真发 action，两边混列就可能让人在「模拟环境」里撤掉真实群的消息。同一判据也用在事件扇出边界上，否则会一边只列虚拟机器人、一边继续把真实群的消息推进观察窗。
- **开关开启时 selfId 白名单不参与筛选。** 虚拟机器人的 selfId 由提供方插件决定，不可能出现在管理员手写的白名单里；继续筛选的话，配了白名单的人永远看不到虚拟机器人。
- **候选集合的变化落在机器人选择层。** 「哪些机器人算可用」按 ADR 0001 归 `src/onebot/`，由调用方传入「是否纳入虚拟机器人」这一个标志。可用性判定、action 通道探测、在线状态推导的判据都不变，只换候选集合。
- **模拟环境不再有任何只在它里面生效的分支。** 服务装配永远创建真实实现，开关只是一个选项；内存实现与写死场景整体删除，WebQQ service 类型收敛成单一形状。消息列表的好感度徽标不再按模拟环境跳过——虚拟机器人在 ChatLuna 库里查不到记录时徽标为空，那是正确答案而不是缺陷。

## 考虑过的替代方案

- **`inject` 提供方插件的 service**：调用更直接，但把两个插件的发布节奏和类型绑在一起，且把「模拟环境的后端」固定成某一个实现。
- **在本插件里实现一台自带场景的假 OneBot 机器人**：不依赖任何插件，但重造沙盒，并把写死的场景换个地方继续维护。
- **虚拟机器人与真实机器人混列**：省掉一处过滤，但把「在模拟环境里误操作真实群」变成一次误点击就能触发的事故。

## 后果

- 场景在提供方插件自己的界面里随手改：建群、加好友、造一条加群申请、以别人的身份发消息进来，一次改动同时验证适配层与实时链路。
- 提供方缺某个 action 时，观察窗只少对应那一块数据，其余部分照常可用。
- 本仓库的测试不装提供方插件、不引用它的类型，只断言「拿到这种形状的机器人时行为正确」。
- 不推翻既有决策：ADR 0001 的分层不变（候选集合的判定仍在 `src/onebot/`，适配层不承接这件事）；ADR 0002 已为两个插件共存做的样式隔离不受影响；ADR 0003 的配置边界不变，配置键 `webQQMockEnvironment` 不改名，只改说明文案，规格 module 仍不引用 `koishi`。
