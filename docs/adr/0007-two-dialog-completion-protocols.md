# ADR 0007：输入对话框与确认对话框不合并成一套协议

## 状态

已接受。

## 背景

架构复查提议把这两个对话框合并。它们的状态袋确实同构：各有一个开关、标题、描述、确认按钮文案，各有一个模块级 `let submit`，加起来 16 个名字平铺给模板。看上去是同一台状态机写了两遍。

但完成协议不同：

- **输入对话框**：确认后宿主先关闭，再跑动作，失败只落到共享的错误横幅上。发射后不管。
- **确认对话框**：组件自持提交态，显示「处理中...」并禁用两个按钮，await 动作，成功才关闭，失败时留在原地。

## 决策

两套协议都保留。共享的部分——错误落点与提交回调的生命周期——收进一个 module；协议本身留在各自的组件里。

判据是两类场景对失败的容忍度不同：

- 设置好友备注、群名片、专属头衔失败时，值没写上，用户看一眼错误横幅就知道要重来。把他扣在对话框里不提供任何额外信息。
- 删好友、踢人失败时，乐观关闭会让人以为成功了。必须留在原地，而且要能直接重试。

## 考虑过的替代方案

- **统一到 await-and-stay-open**：三个输入型调用点都会多出一个待处理态和「失败后手动关闭」的步骤，为一次备注设置增加两次点击。
- **统一到 fire-and-forget**：破坏性操作失败后对话框已经消失，重试要重新走一遍右键菜单；而且「删除失败」与「删除成功」在界面上的差别只剩一条横幅。
- **收成一个 Escape 栈并顺带合并**：复查报告的原提议。前提不成立——观察窗那条 Escape 分支根本不管对话框，它只管会话内查找、转发目标、多选模式与回复目标；三个基于共用 Dialog 的浮层由 `DialogContent` 自己的 `@keydown.esc.stop.prevent` 处理，那个 `.stop` 正是分层生效的原因。要收成一个栈得先拆掉 `.stop`，而那条挂载路径被项目的生产兼容规则点名保护（生产 Koishi 里换回 Reka 的 Presence 挂载路径会让内容退化成注释节点，表现为全屏模糊但弹窗内容不存在）。

## 后果

- 两个对话框组件各自保留完成协议，module 只统一 spec 与回调生命周期，对外 8 个名字（原先 16 个）。
- 新增一种对话框时先问它属于哪一类。两类都不合适才考虑第三种协议，而不是往现有两类里加开关。
- 下一次架构复查看到「两份相似的对话框状态」时先读这条：相似的只是状态袋，协议不相似。
