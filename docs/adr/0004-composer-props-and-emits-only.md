# ADR 0004：输入区组件对外只有 props 与 emits

## 状态

已接受。

## 背景

**输入区**从观察窗 SFC 里抽成独立组件后，它和会话层之间有五条真实需求：会话层要拿到可发送内容并执行发送 RPC；发送结束后焦点要回到可编辑区；消息右键菜单的「提及」要插进当前**草稿**；消息列表要知道**发送区占位**；切换会话要清空草稿与**待发附件**。

用 `defineExpose` 可以一次性解决全部五条，仓库里也有先例（消息列表暴露 `scrollToMessage`）。但输入区不是「一个可以被外部驱动的编辑器」：它持有草稿 token、光标、输入法状态、提及菜单与待发附件，一旦暴露方法，调用方就能在这些状态之间制造出中间态，而这些中间态没有任何测试面覆盖。同时，把可编辑区或发送控件的 DOM 引用交出去，等于让别人来量高度、来放光标，输入区就失去了对自己不变量的控制。

## 决策

输入区对外只有 props 与 emits，不使用 `defineExpose`，不暴露任何 DOM 引用。

- **发送**：`submit` 事件带出一个**发送元素构造器**与一个 `complete` 回调。会话层先拿发送锁，再在自己的 `try` 里调用构造器并执行 RPC，然后用 `complete({ sent, restoreFocus })` 回报结果；输入区只在 `sent` 为真时清空草稿、提及菜单与待发附件，并按 `restoreFocus` 决定是否把焦点还回可编辑区。交出构造器而不是现成的元素，是因为附件转字节会失败：只有让它和 RPC 落在同一个 `try` 里，读文件失败才能沿用同一句错误文案，而且发送锁能在转字节之前就锁上（大视频转 base64 期间可编辑区必须已经是禁用态）。发送锁由会话层持有并作为 `sending` prop 传入，因此「发送中禁用可编辑区」和「不双发」都不需要输入区认识 RPC。
- **外部提及请求**：走 `v-model:mention-request`，输入区消费后立即回收成 `undefined`。回收是接口的一部分：不回收则同一个成员无法被连续插入两次。
- **切换会话**：由不透明的 `chat-key` prop 驱动。输入区据此清空草稿、提及菜单与待发附件，但不认识会话类型与 peerId。「切会话时清什么」属于输入区的接口语义，所以必须由一个显式 prop 表达，而不是靠父层给组件换 `key` 隐式重挂载——后者会把这条语义藏进调用点，输入区自己的测试也就断言不到。
- **发送区占位**：对外只给一个数字，用 `update:send-space` 事件推给会话层。发送控件自身高度不出接口，作为 CSS 自定义属性挂在输入区的 `form` 上——它唯一的消费者是附件缩略图，就在 `form` 内部。
- **留在会话层**：发送 RPC 与错误文案、回复目标、提及候选的来源（群成员）、以及「是否渲染输入区」的门禁（发送功能开关与多选模式）。多选模式下的固定占位值也由会话层计算，输入区不认识多选模式。

## 考虑过的替代方案

- **`defineExpose` 暴露 `focus()` / `insertMention()` / `buildElements()`**：调用点更短，但把输入区变成可被外部驱动的状态机，且这些入口全都绕过组件接口，测试要么摸内部、要么覆盖不到。
- **注入编辑器端口 + 内存假编辑器**：可以在没有 DOM 的环境里测逻辑，但生产只有一种可编辑元素，端口只为绕开测试环境而存在；假编辑器编码的是我们对 DOM 的假设，而真实缺陷恰恰长在假设不准的地方。
- **父层用 `:key="chatKey"` 重挂载输入区**：不需要新 prop，清空由卸载顺带完成，但「切会话清什么」变成调用点的隐式约定。

## 后果

- 会话层多了一个回调风格的 `submit` 契约，与仓库里既有的 `confirm(target, resolve, reject)`、`save(input, complete)` 一致。
- 输入区的全部行为都能在一次挂载上断言：传 props、改可编辑区 DOM、派发真实事件、读 emits 与渲染结果。
- 新增输入区能力时，如果发现「必须暴露一个方法才能接上」，那是接口设计出了问题的信号，不是可以放宽这条 ADR 的理由。
