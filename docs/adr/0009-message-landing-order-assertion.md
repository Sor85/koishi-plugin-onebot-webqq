# ADR 0009：消息落地的顺序由注入的假实现断言，生产代码不返回步骤清单

## 状态

已接受。

## 背景

**消息落地**有一条真实的顺序不变量：收到可见 Bot 的消息后，必须先记录 Bot 活动，再记小胶囊计数，再落 WebQQ 实时消息，最后刷新空闲日程。前两步的先后尤其要紧——收到真实消息本身已经证明 action 通道刚刚可用，所以要先记活动再让 WebQQ 读 Bot 状态；反过来的话，适配器仍上报 OFFLINE 时 WebQQ 会永久排除该 Bot。

这条不变量此前没有 interface。守卫是三对源码位置比较：断言某个字符串在源文件里的首次出现位置小于另一个。这种断言有两重问题。它证明的是「源码里这一行排在那一行前面」，而不是「运行时先做了这件事」；而且取首次出现位置意味着它悄悄依赖那几个字符串不出现在任何更早的注释里——同一个文件的注释里已经出现过其中一个方法名，今天没有误判只是因为断言匹配的是完整表达式。

架构复查提议让落地流程返回一份落地结果，其中带一个步骤清单，测试直接比对该清单。

## 决策

把扇出收成一个 module，四个下游依赖全部注入；顺序由测试的假实现按调用次序记录，断言那个事件序列。**生产代码不返回步骤清单，也不以任何形式对外暴露「我依次做了什么」。**

假实现要同时记录**调用**与**完成**两类事件。只记调用抓不到真正的回归：前两步是同步调用，后两步是 `await`；如果有人删掉其中一个 `await`，只记调用的次序数组不会变化，断言照过——而那恰恰是最可能出的错。记完成之后，删 `await` 会让后一步的开始跑到前一步的完成之前，序列立刻不同。

## 考虑过的替代方案

- **返回步骤清单（复查报告的原提议）**：断言强度与本决定相同，区别只在这份「次序」由谁承担。让生产代码承担意味着每条消息都要攒一次数组，而唯一的消费者是测试。这是把测试钩子伪装成 interface——它看起来像返回值，实际没有任何生产消费者；将来有人想删掉它时，也无法从调用方推断它当初为什么存在。
- **改进源码位置断言**：换成正则、加全文唯一性检查、断言只出现一次。无论怎么改进匹配方式，它守的仍然是源码里的行序，不是运行时的执行序。
- **保留一条源码断言专门守 `await`**：把刚要拆掉的那种断言换个地方留下来。
- **只记调用不记完成**：见上，抓不到删 `await`，而这条不变量有一半意义就在「上一步做完才做下一步」。

## 后果

- 顺序不变量第一次能在运行时被证明。改错次序、或删掉 `await` 让后两步并发，都会让事件序列断言变红。
- 扇出 module 的接口保持窄：吃一个会话，不返回供测试观察用的东西。为了让测试看得更多而加宽它，需要先推翻本 ADR。
- 装配层回到纯接线，符合 ADR 0001 对运行时装配层「只创建和传递共享依赖，不写业务流程」的定位。
- 将来若真出现非测试的消费者需要知道落地做了哪些步骤（例如要把落地结果写进诊断日志），那时再加返回值是合理的。判据是「有非测试的消费者」，不是「测试想看」。
